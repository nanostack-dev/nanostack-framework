# Nanostack Framework agent guide

This repository contains reusable Go service primitives and lifecycle wiring. Its local guides are sufficient for standalone work; a shared workspace or installed skills is an optional enhancement.

## Read by task

- Domain names or ownership: read [CONTEXT.md](CONTEXT.md) and [boundaries](docs/boundaries.md).
- Package changes or service integration: read [current architecture](docs/technical/architecture.md), then the affected package guide in [the index](docs/README.md).
- First checkout or environment failure: read [setup](docs/development/setup.md) and [troubleshooting](docs/development/troubleshooting.md).
- Repositories or searches (`nanorepo.Implement`, `nanorepo.Search`, `Postgres.Scopes`), in the framework or for a service: read [Repositories](docs/generated-code.md#10-repositories-nanostack-gen-repo) and [Tenant scopes](docs/generated-code.md#tenant-scopes) before writing a declaration.
- Code changes: follow [testing](docs/development/testing.md); database behavior needs the documented PostgreSQL integration tests.
- Public API changes, compatibility checks or release work: read [publishing and consumer upgrades](docs/runbooks/deployment.md), [rollback](docs/runbooks/rollback.md) and [existing decisions](docs/adr/README.md). Check compatibility with the consumer build in that runbook. `apidiff` never finishes on this module's generic methods and fills the machine's memory.

## Boundaries and invariants

- New framework code goes in the layered trees: `core/` (runtime: lifecycle, config, log, fault, validate, secret), the integrations `http/` (the HTTP boundary), `pg/`, `redis/` and `otel/` (nano modules), and `gen/` (tooling: the nested `gen` module, with the CLI at `gen/cmd/nanostack`). A package imports only its own layer and the layers below: `core/` imports no integration and no tooling package, and an integration does not import `gen/`. The root module never requires `gen`. No layered package imports `modules/`, `app/`, Fx or zerolog. `pkg/functional` is the leaf layer below `core/` (plan section 06, `internal/layers.Leaves`): it is its own module with no framework dependency, and every layer may import it. No layered package imports any other `pkg/` package, with one listed exception that ends when each primitive moves to its layered home: an integration package may import the primitives in `internal/layers.AllowedLegacy` (`pkg/db/transactor`, `pkg/db/pgerr`, `pkg/jetx`, `pkg/tracing`, `pkg/health`, `pkg/apisec`), which carry no Fx and no zerolog. `internal/layers` tests these rules, test and integration files included, and depguard reports them. `pkg/` (reusable primitives) and `modules/` (thin Fx lifecycle wiring) are legacy and still use Fx; new lifecycle code implements the `core/nano` interfaces (`Starter`, `Stopper`, `Runner`, `HealthChecker`) for [generated wiring](docs/generation.md#wiring-nanostack-gen-wire). `core/nano` imports only the standard library and lower core packages (`core/log`, `core/secret`), never a third-party module. Products own tenancy, authorization policy, domain models, queue names and payloads, generated application code and fixtures.
- Reuse the existing framework primitive before adding a parallel API. Keep public errors, cancellation and compatibility explicit; do not silently discard failures.
- Use `pkg/functional` for collection transformations and optional/result values. Read its current source and [API guide](pkg/functional/README.md): absence and failure are separate states. Plain loops are appropriate for side effects, early exit or a functional form that reads worse; state the reason in review.
- Pass `context.Context` first where needed, respect cancellation and wrap propagated errors with `%w`.
- Database query execution uses `pkg/db/transactor`; `pkg/jetx` owns expression/filter helpers. Keep constraint names application-supplied and transport errors out of the data layer. Use generated Nanostack DB model scan destinations, or alias every column for a custom destination; enable strict scanning in affected integration suites.
- Tenant scopes are declared once per project by column name (`Postgres.Scopes`, `Postgres.ContextScopes`). A search covers every tenant column it reads: `Scope` for a hard column (the caller passes the value, taken from the authenticated principal, never the request body), the registered `ScopeFunc` for a context column, or `Unscoped(column, "why")` only while another hard column of that table stays covered. Never silence a scope error another way; a search is never unscoped as a whole. Hand-written queries count only NOT NULL scope columns; a derived method must also name each context scope column, nullable or not, by its `Postgres.ScopeNames` short name (no parameter) or its Go field.
- Durable product work belongs in a database-backed queue or persisted state, with cancellation and joined shutdown for worker lifecycles. Framework code does not invent product scheduling semantics.
- Generated functional families come from `go -C pkg/functional generate ./...` (a nested module); app OpenAPI and database generation remain owned by the consuming application.

## Delivery and documentation

Fetch the default branch and edit in an isolated worktree; preserve the primary checkout. Use Conventional Commits, run affected tests plus the module build and vet checks, and open a focused PR. Report the exact verification and any skipped integration tests. Review requests produce findings and a verdict before implementation.

Update authoritative docs in the same PR when behavior, a reusable fix, a domain term or a consequential choice changes. Current behavior belongs in `docs/technical/` or its package README, verified development repairs in `docs/development/`, operational procedures in `docs/runbooks/`, and vocabulary in `CONTEXT.md`. Preserve the [dated decision log](docs/decision-log.md); new ADRs record real alternatives and consequences, and reversals supersede earlier records. Keep [the index](docs/README.md) current. `AGENTS.md` is the sole agent guide filename.
