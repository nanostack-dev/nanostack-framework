# Benchmarks: v0.23.0-beta.1 against the v0.22 path

This page compares the hot paths of the beta with the legacy (v0.22) path
that echopoint and anchor run today. Both paths are in this repository, so
each pair runs the same input through both sides in one test binary.

A regression is a change of more than 20% in ns/op or allocs/op on a hot path
against legacy. Each regression has a profile and a fix in
[Findings](#findings).

The report has two runs. The first run measured the beta before the audit
fixes of 2026-11-08 (commit `1de39fa`). Its numbers are kept as they were.
The second run measured the beta after those fixes (commit `350e4fc` plus
the audit fixes in the working tree). Each section shows the first run
("before"), then the second run ("after"). Both runs measure legacy again,
so each run compares like with like on the same machine.

Each run is `-benchmem -count=10` at the default `-benchtime=1s`. The runs
were sequential. The "before" run was on an otherwise idle machine; the
"after" run had a load average of about 2.5 from other work, so read
differences of a few percent between the runs as noise. From the repository root:

```sh

go test ./http/nanohttp/ -run '^$' -bench '^BenchmarkRouter$' -benchmem -count=10 > 2-router.txt

go test ./pkg/jetx/ -run '^$' -bench '^BenchmarkSearchSQL$' -benchmem -count=10 > 5a-searchsql.txt
(cd db && go test ./query/ -run '^$' -bench '^BenchmarkScan$' -benchmem -count=10) > 5b-scan.txt
go test ./core/secret/ -run '^$' -bench '^Benchmark(IsKey|RedactQuery)$' -benchmem -count=10 > 6a-iskey.txt
go test ./core/log/ -run '^$' -bench '^BenchmarkRedaction$' -benchmem -count=10 > 6b-redaction.txt

go run golang.org/x/perf/cmd/benchstat@latest -col /impl 1-requestlog.txt   # and so on; -col /handler for 6b
```

Every sub-benchmark name carries `impl=<side>`, so `benchstat -col /impl`
puts the sides next to each other with the ratio and the p-value. The first
column is the base. The tables below leave out the B/s rows of pair 3.

Profiles come from one longer run of the regressing row, for example:

```sh
go test ./http/nanohttp/ -run '^$' -bench 'Router/impl=beta/case=404' -benchtime=200000x \
  -cpuprofile router404.cpu -memprofile router404.mem -o nanohttp.test
go tool pprof -top -nodecount=25 nanohttp.test router404.cpu
go tool pprof -sample_index=alloc_objects -top nanohttp.test router404.mem
```

### Where the files are

A benchmark that imports both sides sits in the legacy tree. The reason is
`internal/layers.TestNoUpwardImports` and depguard: they forbid a `core/`,
`http/` or `db/` package, test files included, to import `pkg/`, `modules/`
or zerolog. A legacy package may import the layers. The files that import
zerolog suppress depguard on that import line only.

| Pair | File |
|---|---|
| 1 | `pkg/httputil/requestlog/middleware_bench_test.go` |
| 2 | `http/nanohttp/router_bench_test.go` |
| 3 | `http/nanohttp/internal/example/decode_bench_test.go` (the package that has the generated `Validate` and `openapi.yaml`) |
| 4 | `modules/httpserver/errors_bench_test.go` |
| 5 | `pkg/jetx/filter_bench_test.go` (SQL build), `db/query/query_bench_test.go` (scan) |
| 6 | `core/secret/key_bench_test.go`, `core/log/redact_bench_test.go`, `pkg/log/line_bench_test.go` |

### Fairness rules

- Every logger writes JSON to `io.Discard` at Info, unless a row says
  `level=debug`. The legacy logger is built as `modules/logging` builds it:
  `zerolog.New(w).With().Timestamp().Caller()`. The beta logger is `log.New`.
  In pairs 1 and 4 the beta logger also carries the service identity
  (`service`, `env`, `version`), which `modules/logging` does not add. These
  attributes are pre-formatted, so they add bytes but almost no time.
- The response writers are minimal and reused, so the floor is low and the
  difference shows.
- Requests carry an inbound `X-Request-Id`, so neither side mints a UUID.
  Requests come from a private address with `X-Forwarded-For`, so core/log
  walks its trusted-proxy list.
- Code that logs through `slog.Default()` (`problem.Write`, the default
  NotFound of `NewRouter`) gets an `io.Discard` default.

fixes, the router hit and the Option scan are no longer regressions, and

zerolog) and the unmatched request (2.98 µs, which is the bare ServeMux
miss plus 1.3 µs). The unmodelled 500 also stays above, but it is not a hot

## 3. JSON boundary

Request decode of `CreateWebhookRequest` (the example API) in 4 forms:

- `legacy-decode`: `json.NewDecoder(r.Body).Decode`, the body decode of
  oapi-codegen's upstream strict server, without validation.
- `legacy`: what a v0.22 service runs: the OpenAPI request validator of
  `modules/httpserver` (`nethttp-middleware` over kin-openapi, with the
  options of `openAPIValidator`), then the same decode.
- `beta`: `nanohttp.Decode`: `ReadBody`, strict json/v2 and the generated
  `Validate`.
- `beta-read`, `beta-unmarshal`, `beta-validate`: the 3 steps of `beta`.

The 1 KB body uses every member. The 64 KB body fills `description` and the
20 `headers` that the schema allows with 3-byte runes up to their
`maxLength`. This is the largest valid body that the schema accepts.

## 4. Error path

The writers that the strict server's error hooks call:

- `legacy`: `modules/httpserver.StrictErrorHandler` (zerolog), on a request
  that has the request-scoped logger of `requestlog.Contextualize`.

  of `log.HTTPMiddleware`. This is the same wire envelope.
- `floor`: `pkg/fault.WriteJSON`. It does not resolve and does not log. It is
  the floor, not a peer.

## Findings

### bench-router-miss (high): NewRouter does 9 lookups on every 404 and 405

**Status after the fixes: fixed.** `NewRouter` owns a catch-all route (decision log, 2026-11-08: Beta Audit Fixes). A 404 takes 2.98 µs and 66 allocations, a 405 1.78 µs and 31. The text below describes the code before the fix.

`router.allowed` calls `ServeMux.Handler` once for each of 8 probe methods.
On a miss, each `ServeMux.Handler` call computes `matchingMethods` inside
net/http, which walks the routing tree and allocates. So one unmatched
request does 9 such walks.

Evidence (`Router/impl=beta/case=404`, 13.1 µs, 353 allocs):

```
alloc_objects: 88% flat net/http.(*routingNode).matchPath
               85% cum  net/http.(*ServeMux).matchingMethods
               88% cum  nanohttp.(*router).allowed
cpu:           37% cum  net/http.(*routingNode).matchPath
               34% cum  net/http.(*routingNode).matchingMethodsPath
```

Impact: every 404 (scanners, typos, removed routes) costs 70 times chi and
8 times the bare ServeMux. A flood of unmatched paths costs 13 µs of CPU and
7 KB of garbage per request.

Fix: one lookup on a miss. For a miss, `ServeMux.Handler` already returns
its 405 handler, which sets `Allow`, or `NotFoundHandler`. Call that handler
once on a small header-capturing writer, read the status and `Allow`, and
dispatch to `NotFound` or `MethodNotAllowed`. ServeMux lists HEAD whenever a
GET pattern matches, so with `ExplicitHEAD` one extra HEAD probe decides
whether HEAD stays in `Allow`. This brings a 404 to the floor of the bare ServeMux
(1.7 µs, 46 allocs). To go below that floor, register a lowest-precedence
catch-all `/` on the mux in `NewRouter` (and refuse a mux that already has
`/`). Then a miss never makes net/http compute `matchingMethods`, and the
probes that remain are cheap matches. Keep the existing tests that pin
ServeMux behaviour.

### bench-router-hit (medium): NewRouter looks up each matched request twice

**Status after the fixes: fixed.** A hit goes straight to `mux.ServeHTTP` and takes 201 ns, the bare ServeMux cost. The text below describes the code before the fix.

A hit runs `cleanPath`, `ServeMux.Handler` and then `ServeMux.ServeHTTP`,
which does the lookup again. The bare ServeMux takes 202 ns and chi 294 ns.
`NewRouter` takes 468 ns (+59% against chi).

Evidence (`Router/impl=beta/case=hit`, CPU, cumulative): `findHandler` 73%
(called twice), `path.Clean` 22%, `net/url.unescape` 19%,
`nanohttp.cleanPath` 8%.

Fix: the catch-all of bench-router-miss removes the pre-lookup. Every request
then goes straight to `mux.ServeHTTP`, which sets `r.Pattern` and the path
values. Only the catch-all handler, which runs only on a miss, probes the
methods. The unclean-path check is then not needed either, because ServeMux
redirects an unclean path before it matches. Keep the pre-lookup only when
`ExplicitHEAD` is set and the method is HEAD: ServeMux routes a HEAD request
to a GET pattern, so the catch-all would not see it. A hit then costs what
the bare ServeMux costs, 30% less than chi.

### bench-requestlog-summary (medium): the request summary costs twice the zerolog chain

**Status after the fixes: partly fixed.** The summary takes 2.35 µs and 16 allocations (was 3.65 µs and 27), +34% against legacy at 200. The text below describes the code before the fix.

`HTTPMiddleware` takes 3.6 µs and 27 allocations per request. The legacy
chain takes 1.8 µs and 21 allocations.

Evidence (`RequestLog/impl=beta/status=200`):

```
cpu:   40% cum log.writeSummary
       31% cum log.(*contextHandler).Handle
       27% cum log.(*redactHandler).Handle
       14% cum log.mayChange -> 13.5% cum secret.IsKey (10% flat hasFoldedSuffix)
alloc: 21% slices.Grow (log.prepend copies the record)
       17% log.merge (SetAttrs copies the scope on each call)
       16% cum log.queryAttr (url.ParseQuery, a map and a sort)
        8% cum log.WithScope
```

Fix, in order of effect:

1. Make `secret.IsKey` cheap (bench-iskey). This removes most of the 14%.
2. In `redactHandler.Handle`, call `IsKey` once per attribute: record the
   index of the first attribute that may change, and start `clean` there.
3. In `contextHandler.Handle`, stop building a new record per line. Let
   `Attrs` return the scope slice without `slices.Clone`: `merge` already
   makes a new slice on every change, so a slice that a reader holds never
   changes. Then add the scope attributes once, to a record of the right
   capacity.
4. In `WithScope`, allocate the scope with room for 8 attributes. In `merge`,
   append in place when no key repeats and the capacity allows (the
   copy-on-write rule of item 3 then applies to the slice header only).
5. In `queryAttr`, walk the raw query with `strings.SplitSeq` (as
   `redactedQuery` does) and sort a small slice, instead of building a
   `url.Values` map.

### bench-iskey (medium): secret.IsKey compares all 28 suffixes on every miss

**Status after the fixes: fixed.** `IsKey` looks the suffixes up in a table indexed by the key's last byte. A miss takes 13 to 25 ns. The text below describes the code before the fix.

A miss costs 78 to 85 ns, and most keys are misses. A request summary has
about 15 keys (8 attributes, the scope, the query group), so the guard costs
about 1.2 µs per request.

Evidence: the `IsKey` table in pair 6, and `secret.IsKey` at 13.5% of the
middleware CPU and 9.4% of a single log line.

Fix: index the suffixes by their last byte. Fold the last non-separator byte
of the key, look up the suffixes that end with that byte in a `[256][]string`
table built at init, and compare only those. The largest bucket (`y`, the
10 compound `*key` suffixes) has 10 entries; the others have 0 to 5, and the
common keys (`request_id`, `status`, `route`, `path`, `client_ip`) fall in
buckets of 0 to 5. A miss then costs about 5 to 20 ns. The suffix
list and the matching rules do not change, so the key tests stay valid as
they are.

### bench-scan-option (medium): an Option field allocates 3 times per non-NULL value

**Status after the fixes: item 1 done, item 2 rejected for now** (decision log, 2026-11-08: Beta Audit Fixes). The scan takes 1.34 ms and 17,119 allocations (was 1.79 ms and 18,619), +11% against pointer fields. The text below describes the code before the fix.

`assignOption` runs for each non-NULL Option value and does 3 allocations:

```
alloc_objects, qrm.assignOption (qrm/option.go):
  64: tmp := reflect.New(elem).Elem()              3.0M
  67: if implementsScannerType(elem) {             2.9M  (reflect.New only to get the pointer type)
  75: return optional.Set(field, tmp)              3.4M  (x.Interface() boxes the value for Option.Scan)
cpu: implementsScannerType 290 ms of 430 ms in assignOption (6.4% of the scan)
```

A pointer field does 1 allocation (`reflect.New` of the pointee).

Fix:

1. Decide Scanner or not once, in `classifyOption`, and keep the result in the
   field mapping (for example, an `optionalScannerType` kind next to
   `optionalType`). Do not call `implementsScannerType` per value.
   (`implementsScannerType` is in the upstream file `qrm/utill.go`; its
   `reflect.New(t).Type()` could be `reflect.PointerTo(t)`, a candidate
   upstream PR.)
2. Write the value in place. `internal/optional` already caches per type.
   Add the offsets of the `v` and `present` fields of `functional.Option`
   (this repository owns the layout, and a test can pin it). Assign with
   `reflect.NewAt(elem, unsafe.Add(base, off)).Elem()` and the same `assign`
   that a `*E` field uses, then set `present`. This removes `tmp`, the boxing
   and the `Scan` call. An Option field then allocates less than a pointer
   field, because the value is in the struct and not on the heap.

### bench-validate-allocs (low): the generated Validate builds a JSON Pointer per field

**Status after the fixes: not changed** (decision log, 2026-11-08: Beta Audit Fixes): the proposed fix does not remove the cost, because `document.lookup` walks the pointer on every presence query.

This is not a regression: the beta decode is 14 times faster than the
validator path that it replaces. But `Validate` is 65% of the 1 KB decode
(6.2 µs, 91 allocations), 3 times the json/v2 unmarshal.
`validate.Path.Field` and `Path.Index` concatenate the pointer string on every
call, for every field, also when there is no error.

Fix: make `Path` keep the parent and the token, and build the pointer string
only in `Errors.Add`. A valid body then allocates no pointer string, and an
invalid body pays only for the fields that fail.
