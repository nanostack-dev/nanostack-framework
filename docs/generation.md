# Generation

Generation is explicit: every generated file is committed, and `nano gen -check` proves it is current. `nano gen` runs oapi-codegen in-process, at a pinned version. Migrations and go-jet stay with the service until the pipeline's db step lands.

## OpenAPI

`nanogen/project.go` declares the spec, the server package and the Go clients. The pipeline's api step generates them and splits the server by OpenAPI tag ([the tag split](#the-tag-split)). Then validate writes the request validators into the server package ([the pipeline](#the-pipeline-nano-gen)):

```go
API: &project.OpenAPI{
	Spec:   "cmd/http/openapi.yaml",
	Server: project.Package{Dir: "internal/api"}, // File: default api.gen.go
	Clients: []project.Client{
		{Dir: "cmd/it/client", Package: "client", PlainTypes: true}, // File: default client.gen.go
	},
},
```

Framework home:

- `gen/api` is `nano gen api`, the api step: oapi-codegen v2.8.2 in-process ([decision log](decision-log.md#2026-11-08-nano-gen-runs-oapi-codegen-in-process))
- `gen/validate` is `nano gen validate`, which writes the request validators
- `http/nanohttp/oapitemplates` holds the server's template overrides

### Server generation

The server is oapi-codegen's strict server on `net/http`'s ServeMux, with its strict template replaced by the override in `http/nanohttp/oapitemplates`. The override decodes bodies through `nanohttp.Decode`, runs the generated validators and sends every error through `http/problem`. [The HTTP boundary](http-boundary.md) describes the runtime contract.

The api step fixes this configuration; a project declares only the package. Written for oapi-codegen's command, it is:

```yaml
package: apigen
output: api.gen.go
generate:
  models: true
  std-http-server: true
  strict-server: true
additional-imports:
  - package: github.com/nanostack-dev/nanostack-framework/http/nanohttp
  - package: github.com/nanostack-dev/nanostack-framework/http/problem
output-options:
  user-templates:
    strict/strict-http.tmpl: <path to http/nanohttp/oapitemplates/strict/strict-http.tmpl>
    union.tmpl: <path to http/nanohttp/oapitemplates/union.tmpl>
```

`union.tmpl` makes the `As<Variant>` and `Discriminator` methods of a `oneOf` or `anyOf` type decode with `nanohttp.Unmarshal`, the strict json/v2 options the validators use. The upstream template decodes with `encoding/json` v1, which matches member names case-insensitively: a handler could read `"TOKEN"` while validation checked `"token"`.

The override calls the `Validate` and `validateParams` methods that `nano gen validate` writes, so the package does not compile until they exist and match the spec. The pipeline runs validate right after api.

### The api step

- **One oapi-codegen.** The `gen` module links oapi-codegen v2.8.2 as a library, the release the overrides are cut from (`oapitemplates.OapiCodegenVersion`). A service's module can still resolve another version through its own requirements. The step reads the version from the binary's build information and fails with exit 3 on any other version, or on a `replace` of the module: `fix: go get github.com/oapi-codegen/oapi-codegen/v2@v2.8.2`. To upgrade, diff the upstream `strict/strict-http.tmpl` and `union.tmpl` against the overrides, then move the pin.
- **The same bytes as oapi-codegen's command.** Each output starts with `// Code generated by nano gen api from <spec>. DO NOT EDIT.`, so the orphan scan knows it. In the server file and each client file, the rest is what `go run github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@v2.8.2` writes for the same configuration, byte for byte; a golden test in `gen/api` proves it on the spec of `http/nanohttp/internal/example`.
- **The package name.** The server package is the one its Go files declare, or the name of its directory when it has none. A client states its `Package`, because a directory such as `clients/go` has no usable name.
- **Clients.** A client holds the models and a client type in one file. The step generates the server first, then each client, one at a time: oapi-codegen keeps its options in package state. Each output loads the spec again, so a client's changes never reach the server.
- **`PlainTypes`** drops the server's Go type hints from a client's copy of the spec: every `x-go-type` except `string`, every `x-go-type-import`, and the `x-go-type-skip-optional-pointer` next to an `x-go-type` of the `nullable` package, so the client keeps the pointer that sends null. It walks the parsed document, so a hint in a file that a `$ref` names goes too. It replaces anchor's `scripts/client-spec.sh` and its gitignored intermediate spec; on anchor's spec, both give the same 40,020-line client.
- **Files only.** A remote `$ref` is an error: generation reads only local files. Copy the remote schema into the repository.
- **Outputs stay inside.** The spec may sit outside the directory nano runs on, such as a client module's `../../apps/anchor/cmd/http/openapi.yaml`. The server and client directories may not (design P10), and they may not sit in a nested module: a module beside it, or under it, declares its own `nanogen/project.go`.
- **One output per directory.** Each output holds the models of the whole spec, so the server and the clients each need a package of their own. `API.Server.File` may not be `validate.gen.go`, the file validate writes next to the server, or `handlers.gen.go`, the file of the tag split.
- A `//go:generate` line that runs oapi-codegen is an error at its line: the api step replaces it.

`nano gen api -spec <file> -dir <server dir>` runs the step alone, with `-client <dir> -client-package <name> [-plain-types]` for one client.

### The tag split

The api step splits the server by OpenAPI tag. Next to the server file it writes `handlers.gen.go`, with the same header ([ADR 0024](adr/0024-api-split-by-tag.md)):

- one interface per tag, named after the tag: `Email` gives `EmailServer`, `Status pages` gives `StatusPagesServer`. It holds the methods of the tag's operations, as `StrictServerInterface` writes them;
- `Handlers`, which implements `StrictServerInterface`: each method passes the request to the handler of the operation's tag. Its fields are unexported;
- `NewHandlers(email EmailServer, …) (*Handlers, error)`, with one parameter per tag, sorted by interface name. It refuses a nil handler and names its tag: `NewHandlers: the handler of tag Email is nil`;
- `var _ StrictServerInterface = (*Handlers)(nil)`. `StrictServerInterface` itself does not change.

A handler takes only the services of its tag, and its constructor returns the tag interface:

```go
type emailHandler struct{ emails emailsvc.EmailService }

func NewEmailHandler(emails emailsvc.EmailService) EmailServer { return &emailHandler{emails} }
```

A missing method is then a compile error in the handler's own file. The manifest lists `api.NewEmailHandler` and `api.NewHandlers` in `nano.Providers`, without `nano.Bind`. The server's `NewHTTPHandler` takes `*api.Handlers` as its `StrictServerInterface`.

**Tag rules.** The api step checks the spec before it generates the server. Each problem is an error at the spec line that holds it:

- every operation has exactly one tag: a tag is a handler boundary;
- every tag an operation uses is declared under the top-level `tags`, and every declared tag is used;
- no tag is declared twice, and every tag gives its own Go name: `Status pages` and `StatusPages` would both become `StatusPagesServer`;
- a tag gives a Go name that starts with a letter, and that name is not one the server already declares, such as a schema named `EmailServer`.

```
cmd/http/openapi.yaml:212: operation sendEmail has no tag
  fix: add one of the declared tags: Access, Email, Licensing
cmd/http/openapi.yaml:9: tag Membership is declared but no operation uses it
  fix: delete it, or tag an operation with it
```

A module that generates only clients checks no tag rule: its server, and its tags, live in another module.

**A handler that lacks a method.** go build reports `*emailHandler does not implement EmailServer (missing method SendEmail)` in the handler's file. The pipeline reports it too, from wire, which loads every handler package the manifest imports, and the fix holds the method in full:

```
internal/api/email_api.go:14: *emailHandler does not implement EmailServer (missing method SendEmail)
  fix: add the method of EmailServer: func (h *emailHandler) SendEmail(ctx context.Context, request SendEmailRequestObject) (SendEmailResponseObject, error)
```

A method with the wrong signature gets `give SendEmail the signature of EmailServer:` and the same declaration. A handler in another package, such as an echopoint feature package, gets the server's types qualified by package name: `apigen.SendEmailRequestObject`. wire reports no other compile error of a dependency; go build does. When no provider returns a tag interface, wire's fix names the provider to add: `add a provider that returns api.EmailServer to nano.Providers in cmd/app/manifest.go`. A `nano.Bind` whose type lacks a method gets the full method in its fix too.

### Unenforced schema features

A schema feature the validators cannot enforce, such as a `oneOf` over a Go type that is not an oapi-codegen union, fails `nano gen validate` with exit status 1, at the line of the schema. The generated file is still written, and it lists every gap. Change the schema, or accept the gap with the `x-nano-unenforced` extension. Its value is the reason, which may not be empty. It covers that schema and every schema under it:

```yaml
Shape:
  x-nano-unenforced: "the handler checks the variant"
  oneOf: [...]
```

An extension that accepts no gap is an error too, so it cannot hide the next one. The extension replaces the `-allow` flag ([ADR 0023](adr/0023-nano-gen-pipeline.md)).

### Patterns

`pattern` is an ECMA-262 regular expression. `nano gen validate` translates it to RE2 at generation time and fails on what RE2 cannot express (lookaround, backreferences). Where ECMA-262's u and non-u modes differ, the u mode is the reference: a pattern matches code points, and `\u{...}`, `\p{...}` and surrogate pairs such as `\uD83D\uDE00` are one character. An escape of a letter or digit that ECMA-262 does not define, such as `\a`, `\z`, `\Q` or `\pL`, is an error, because RE2 gives it another meaning. A backslash before punctuation stands for the character itself.

## Database: `nano gen db`

Package: [`gen/db`](../gen/db). Generator: the Nanostack DB fork of go-jet ([`db/generator`](../db/generator)). The pipeline runs this step first, from the `Postgres` declaration of `nanogen/project.go`:

```go
var Project = project.Project{
	Postgres: &project.Postgres{
		Name:  "anchor",                             // writes internal/db/gen/anchor
		Image: "timescale/timescaledb:2.23.0-pg18", // default postgres:18-alpine
		// Migrations: "migrations", Out: "internal/db/gen", Schema: "public" are the defaults.
	},
}
```

**What a run does.** It applies the golang-migrate files of `Migrations` to an empty database with `pg/nanomigrate`, in-process: no `migrate` CLI, no shell script. The database is a container of `Image`, started through testcontainers for the run, or a scratch database on the server that `NANO_GEN_DATABASE_URL` names, created for the run and dropped after it (the user needs `CREATEDB`). The pipeline owns that server for the whole run and stops it at the end. go-jet then renders the models and the table types of `Schema` in memory: `<Out>/<Name>/<Schema>/{model,table,view,enum}/*.go`. Every file starts with `// Code generated by nano gen db. DO NOT EDIT.`, so the file of a dropped table is an orphan. The type mapping is go-jet's: pointers for nullable columns, `pq.StringArray` for one-dimensional `text[]`, the enum types of the schema. A failing migration is an error at the migrations directory; nothing is written.

**`UniqueKeys`.** Each table type gets one method, read later by `nano gen repo` with `go/parser`, so the repo step needs no database:

```go
// UniqueKeys lists the keys of users that match at most one row, by constraint
// or index name, with the key columns in index order: [...]
// Not a key: idx_users_active_name: partial index WHERE (status = 'ACTIVE'::user_status).
// Not a key: idx_users_lower_email: expression key.
func (UsersTable) UniqueKeys() map[string][]string {
	return map[string][]string{
		"users_pkey":             {"id"},
		"idx_users_external":     {"tenant_id", "external_id"}, // WHERE (external_id IS NOT NULL)
		"users_tenant_email_key": {"tenant_id", "email"},
	}
}
```

A unique index is a key when equality on its key columns, with values that are not NULL, matches at most one row: it is valid and not deferrable, it has no expression key, its predicate is absent or only `<key column> IS NOT NULL`, and no key column compares under a nondeterministic collation that the index does not use. `INCLUDE` columns are not key columns. Every other unique index is a `Not a key` line with its reason. A column named `unique_keys` is an error, because the method would hide its field. [`gen/db/testdata/keys`](../gen/db/testdata/keys) has one index of each shape and its generated code.

**`ColumnTypes` and `ForeignKeys`.** Each table type gets two more methods after `UniqueKeys`. `nano gen repo` reads them with `go/parser` too. `ColumnTypes` gives the catalogue type of each column, by column name, in column order: The type name from `pg_type`: the base type at the end of a chain of domains, `_text` for a `text[]` column or an array of a text domain, the name of an enum, and `schema.name` for a type of another schema or a type that has the name of a `pg_catalog` type (`billing.status`, `public.path`). The column kind of the table type cannot tell `text` from `inet`, `jsonb` or `uuid`, which all are `ColumnString`. `ForeignKeys` gives the foreign keys of the table, in constraint name order, with the referencing and the referenced columns in key order. `ReferencedSchema` is set only for a key to a table of another schema:

```go
func (EventsTable) ColumnTypes() map[string]string {
	return map[string]string{
		"at":         "timestamptz",
		"payload":    "jsonb",
		"source":     "inet",
		"tenant_id":  "text",
		"user_email": "text",
	}
}

func (EventsTable) ForeignKeys() []postgres.ForeignKey {
	return []postgres.ForeignKey{
		{
			Name:              "events_user_fkey",
			Columns:           []string{"user_email", "tenant_id"},
			References:        "users",
			ReferencedColumns: []string{"email", "tenant_id"},
		},
	}
}
```

A column named `column_types` or `foreign_keys` is an error, for the same reason as `unique_keys`. `postgres.ForeignKey` (`mysql.ForeignKey`, `sqlite.ForeignKey`) is the type of the element; nothing reads the method at run time.

**`nanogen.sum`.** `<Out>/<Name>/nanogen.sum` records every input (the image, the schema, the versions of the `gen` and `db` modules, and the sha256 of each migration file) and the sha256 of every output. While each input matches, each listed output matches its hash and no other `nano gen db` file is under `<Out>/<Name>`, a run reads no database: it keeps the committed files. So `go tool nano gen` after a handler change needs no Docker. When something differs, the run needs a database, and says why:

```text
nano gen db: migration 000042_add_notes.up.sql is new since internal/db/gen/anchor/nanogen.sum, and Docker cannot start timescale/timescaledb:2.23.0-pg18: [...]
  fix: start Docker, or set NANO_GEN_DATABASE_URL
```

That exits 3, the code of the environment; the other steps still run on the models on disk, and no model is deleted. A framework upgrade changes a version line, so the first run after it needs a database too.

**CI: `nano gen -check -fresh`.** `-fresh` ignores `nanogen.sum` and always generates from the migrations, so CI proves that the committed models and keys are what the migrations produce, and a sum cannot hide a stale model. A service adds the job with its db-step adoption, before it binds any repository:

```sh
GOWORK=off go tool nano gen -check -fresh   # needs Docker, or NANO_GEN_DATABASE_URL to a service database
```

On a pull request whose migration drops a unique key or renames a column, the job fails on the table file (`stale internal/db/gen/anchor/public/table/users.go`) until the author regenerates. Once `nano gen repo` binds repositories, a derived method that relied on the key fails in the same run.

`nano gen db -name <name> [-migrations d] [-out d] [-schema s] [-image i] [-fresh] [-check]` is the single run, with the fields of the declaration as flags.

## Configuration: `nano gen config`

Package: `gen/config`. Runtime: `core/config`.

Source: a plain Go struct. Struct tags declare each setting, and the field's doc comment is its description.

- `config:"name[,optional]"` names the setting in lower snake case. Nested structs add a path segment (`billing.due_days`). Every exported field needs one; `config:"-"` skips a field.
- `env:"NAME"` overrides the environment variable, derived from the path by default (`BILLING_DUE_DAYS`).
- `default:"value"` is parsed and validated at generation time. Defaults of `encoding.TextUnmarshaler` types (such as `slog.Level`) are checked only when `Bind` runs; bind the defaults in a test.
- `defaultenv:"NAME"` takes the default from another environment variable first: the setting reads `NAME` only when its own variable and the config files leave it unset, then the literal `default`. One variable can so feed two settings, as the env of one and the default of the other, while a config file still sets the second apart. `NAME` must not be the setting's own env nor the env of a secret setting, and a secret takes no `defaultenv`. Two settings with the same `env` remain an error. `CONFIG.md` shows the default as ``env `NAME`, else `value` ``.
- `validate:"min=1,max=365"`, `oneof=a b c` and `scheme=https` are the rules.
- A setting without a default is required unless it is optional. Secrets (`secret.Secret` from `core/secret`, the framework's one secret type) cannot have a default and are never read from YAML files. Every printing path shows them as `[REDACTED]`.

Outputs, next to the struct: `config.gen.go` (a reflection-free `Bind`, a redacted `LogValue`, `String` and `GoString`), `CONFIG.md` (the reference of every setting) and `.env.example` (`-env` sets another path).

`nano gen config` loads the package with `-tags=nanogen`, as `nano gen wire` does. That drops `wire.gen.go` and the files that call `Build` (they carry `//go:build !nanogen`), so a renamed `Config` field never blocks regeneration: config writes the new `config.gen.go`, then wire reads it. Keep `Config` in a file without a build tag. The generator replaces its own previous output with a stub, so a stale `config.gen.go` does not block it either.

At start-up, `config.NewSources(config.ProfileFromEnv("config"), config.Env())` layers `config/base.yaml`, then `config/<NANO_PROFILE>.yaml`, then environment variables. `Bind` reports every issue in one `*config.Error` (a list of `config.Issue`) and never shows a secret or a URL password.

## Errors: `nano gen errors`

Package: `gen/errors`. Runtime: `core/fault`. Decision: [ADR 0022](adr/0022-error-catalogue-from-go-interface.md).

Source: one Go interface per package whose doc comment holds `//nano:errors namespace=<name> [type_base=<url>]`. Each method declares one error; its doc comment holds `//nano:error code=<snake> status=<4xx|5xx> title="..." [detail="... {param} ..."]`. `code=` is required: the code and the problem type URI are the client contract and never follow a rename of the Go method.

Outputs, next to the declaration: `errors.gen.go` (a constructor, a typed error and an `Err<Name>` sentinel per error, plus the `Kinds` list) and `ERRORS.md` (the catalogue). The generator type-checks the package and its own output, so a declaration either generates code that compiles or fails with its `file:line`.

## Repositories: `nano gen repo`

Package: [`gen/repo`](../gen/repo). Declarations: [`db/nanorepo`](../db/nanorepo). Runtime: [`pkg/db/transactor`](../pkg/db/transactor). Decision: [ADR 0026](adr/0026-nano-gen-repo.md).

A repository is one interface and its implementation struct. Each method of the interface is, in this order:

1. **hand-written**: the implementation has the method, in a file nano gen repo did not write, or promoted from an embedded field. It wins, and its signature must match the interface;
2. **derived**: its name follows the grammar below on the bound table, so nano gen repo generates it on the implementation, as one call to a helper of the generated base;
3. otherwise **an error** at the interface method, with the signature to paste on the implementation and, when one works, a derivable rename.

**The declaration.** A repository package binds each repository interface to its implementation struct and a go-jet table, inside `func _() { … }` in a file without a build tag, so the compiler, `go vet` and gopls check it and a rename updates it:

```go
func _() {
	nanorepo.Implement[ItemRepository, itemRepositoryImpl](table.Items, itemToDomain)
	nanorepo.Implement[AuditLog, auditLogImpl](table.AuditEvents, nanorepo.NoMapper[model.AuditEvents])
	nanorepo.Base[model.Tenants](table.Tenants) // a base with no interface
}
```

The model row and the domain type come from the mapper, `func(model.Items) Item`. `nanorepo.NoMapper[model.X]` keeps the model rows. The mapper takes no state: it is a function, or a variable of the declaring package set to a function, a function literal or a method value on a type without fields; the base calls it with no dependencies. Two declarations on one table in one package share its base, so they pass the same mapper. Part 1 supports PostgreSQL tables only.

**The base.** `repo_base.gen.go`, one per declaring package, holds a base per table. The implementation embeds it and sets it with the generated constructor; hand-written methods use its members:

```go
type itemRepositoryImpl struct {
	itemsBase
}

func NewItemRepository(db qrm.DB) ItemRepository {
	return &itemRepositoryImpl{itemsBase: newItemsBase(db)}
}

func (r *itemRepositoryImpl) ListActive(ctx context.Context, tenantID uuid.UUID) ([]Item, error) {
	return r.findAll(ctx, r.where.TenantID(tenantID).AND(r.where.Status(model.ItemStatus_Active)),
		r.t.Sku.ASC(), r.t.ID.ASC())
}
```

| Member | What it is |
| --- | --- |
| `t` | the go-jet table, for any statement the helpers do not cover |
| `where` | a typed predicate per column: `X(v)` and `XIn(vs...)` on every column that has an equality; `XAfter`/`XBefore` on numbers and times; `XIsNull` on nullable columns; `XContains` and `XEqualsIgnoreCase` on text columns that are not keys or IDs: a column whose type in `ColumnTypes()` is `text`, `varchar`, `bpchar` (`char(n)`) or `citext` |
| `findOne(ctx, cond)` | the one row matching `cond`, absent when none does; reads `LIMIT 2` and returns `transactor.ErrMoreThanOneRow`, wrapped with the table name, when two rows match |
| `first(ctx, cond, order, more...)` | the first row in an order; end it with a unique column so the row is stable |
| `findAll`, `exists`, `count` | every matching row, whether one matches, how many match |
| `deleteWhere(ctx, cond)`, `updateWhere(ctx, cond, set, more...)` | change the matching rows and return how many; a nil `cond` is an error, not a change to every row |
| `query[T]`, `queryOptional[T]`, `queryMap`, `queryOptionalMap`, `queryMapSlice`, `queryCount`, `exec`, `execAffected`, `page` | the `pkg/db/transactor` functions as methods, with the base's database |
| `queryRow`, `queryRowOptional`, `queryRows` | the same for statements that return the table's rows, mapped with the declaration's mapper |

A nil `cond` on a read means every row. Every helper runs through `pkg/db/transactor`, so it joins the context transaction and keeps the row-lock rules: `findOne`, `first` and `findAll` honour `transactor.ForUpdate`, PostgreSQL refuses the lock on `exists` and `count`, and the two writes refuse it as `Exec` does. Predicate values are typed: `uuid` columns compare as `uuid`, enum columns cast to their type, so their index applies. Other string columns compare as text. A column of another type that the model reads as a string (`json`, `inet`, `uuid`, `tsvector`) gets no `X(v)` and no `XIn(vs...)`, because a text value does not compare with it: write a statement on `b.t`, and a derived method on it is refused. `XContains(term)` calls `searchexec.Contains`, the substring rule of every search: it trims the term and matches without case (`ILIKE ... ESCAPE '!'`), `%`, `_` and `!` in the term match themselves, and a blank term matches every row, also a row where the column is NULL. An index on `lower(col)` does not serve it; a trigram index on `col` does. On PostgreSQL, `XContains` on a column with a nondeterministic collation fails with an SQL error, because `ILIKE` refuses such a collation (`LOWER(col) LIKE` worked there on PostgreSQL 18): write that predicate by hand. A column that the model reads as a string but whose type is not text (`inet`, `jsonb`, `uuid`) gets no `XContains` and no `XEqualsIgnoreCase`, and a table package without `ColumnTypes()` is an error: run `nano gen db`. A view is the exception, because `nano gen db` writes no `ColumnTypes()` on a view yet: the base of a view generates, its string columns keep `X(v)` and `XIn(vs...)`, they get no `XContains` and no `XEqualsIgnoreCase`, and the doc comment of the predicate type names them.

**Derived methods.** A method of the interface without a hand-written body derives from its name:

| Prefix | Example | Runs | Returns |
| --- | --- | --- | --- |
| `FindBy`, `GetBy` | `FindByTenantIDAndSku` | `findOne` (`LIMIT 2`) for one row, `findAll` for a slice | `(functional.Option[D], error)`, `(D, error)` (`sql.ErrNoRows` on no row), `([]D, error)` |
| `FindAll` | `FindAllInternal` | `findAll` on every row | `([]D, error)` |
| `ExistsBy` | `ExistsByTenantIDAndExternalID` | `exists` | `(bool, error)` |
| `CountBy`, `Count` | `CountByTenantIDAndActive` | `count` | `(int64, error)` |
| `DeleteBy` | `DeleteByTenantIDAndID` | `deleteWhere` | `error`, `(bool, error)` (a row was deleted), `(int64, error)` (how many) |

- The properties are the Go field names of the table (`TenantID`, `Sku`), joined by `And`, equality only. `IgnoreCase`, `In`, `OrderBy`, `Or` and the other operators do not derive: the error gives the hand-written body on the base.
- `ctx context.Context` comes first, then one parameter per property, bound by position. A parameter named after another column of the name is an error (`ExistsByTenantIDAndSku(ctx, sku, tenantID)`); a name that is no column binds by position. A parameter has the model field's type, or a named type over it, which the method converts; a pointer is an error, because `=` never matches `NULL`.
- A single-row find, `Option[D]` or `D`, derives only when its columns cover the primary key or a key that `UniqueKeys()` lists ([the db step](#database-nano-gen-db)). Otherwise the error offers a slice, a unique index, or the hand-written body with `first` and an order.
- On a table scoped by `Postgres.Scopes`, the name filters on a scope column first. A name that ends in `Internal` skips the rule **on a read** (`FindAllInternal`, `CountInternal`): the generated comment and `-explain` mark it `UNSCOPED`. A delete across tenants never derives; it is written by hand, where review sees it. When the name splits into columns with its `Internal`, as `FindByIsInternal` on a column `IsInternal`, the suffix is the column's: `FindByIsInternalInternal` skips the rule.
- The rows a find returns are the mapper's domain type, or the model with `NoMapper`.

The generated file is `<file>_repo.gen.go`, next to each declaring file that calls `nanorepo.Implement`: the derived methods of its bindings, each with its SQL in the comment, and a `var _ Iface = (*impl)(nil)` line per binding. When a hand-written body is deleted and nobody reruns nano gen, `go build` fails at that line. When the implementation embeds several bases, a derived method calls the one of its table by name.

**Scope columns.** `Postgres.Scopes` in `nanogen/project.go` names the tenant columns (lower case, each once):

```go
Postgres: &project.Postgres{Name: "anchor", Scopes: []string{"tenant_id"}},
```

A table is scoped when it has one of them as a `NOT NULL` column. A hand-written function that touches a scoped table through its base (a predicate, a helper that takes a condition, a `SELECT`, `UPDATE` or `DELETE` on `b.t`, or a `SELECT` that reads `FROM` `b.t` or a join on it) without a predicate or a reference on a scope column gets a warning, unless its name ends in `Internal`:

```text
warning: internal/repository/users.go:31: ByEmail: condition on users has no tenant_id; this query can read or change another tenant's rows
  fix: add u.where.TenantID(…) to the condition, or name it ByEmailInternal for a trusted system path
```

A warning keeps exit 0. The check is a guard against a forgotten filter, not a proof: a function that builds its condition elsewhere is judged by what it calls. Derived methods are never warned about: their names already follow the scope rule.

**All or nothing.** The generator loads the package with every file it wrote replaced by an empty file, so a stale output never blocks a run and a method a previous run derived never counts as hand-written. It resolves every method, then type-checks the package with the new files. A compile error that remains is reported at its line, beside every method that does not resolve, and nothing is written. An import of a generated file that the module cannot load, such as `pkg/db/transactor` in a module that has never imported it, is reported at the declaration with the `go get` that adds it. Every declaration problem is reported in one run, each at its line with a fix: a declaration that is not an interface and a struct of this package, a mapper with state, a table of another dialect, a hand-written name that clashes with a generated one, an implementation that does not embed the base its derived methods run on, a table package without `UniqueKeys` (run `nano gen db`), a hand-written file in the place of an output. A column that the base on disk had and the table lost is reported as a migration's rename, with the rename first.

**The command.** `nano gen repo [-dir d] [-scopes tenant_id,org_id] [-check] [-explain [Iface|Search…]]` is the single run on one package. `-check` writes nothing and exits 1 on a stale output, or on an orphan: a `<file>_repo.gen.go` whose declaring file binds nothing any more, which a run deletes. `-explain` prints how each method of each bound interface, or of those named, resolves, and writes nothing:

```text
ItemRepository on *itemRepositoryImpl (table items, scope tenant_id)
  FindByTenantIDAndSku           derived: SELECT * FROM items WHERE tenant_id = $1 AND sku = $2 LIMIT 2 -- at most one row: items_tenant_sku_key (tenant_id, sku); a second row is ErrMoreThanOneRow
  FindAllInternal                derived, UNSCOPED (Internal): SELECT * FROM items
  ExistsByTenantIDAndName        hand-written repository.go:98
                                 note: the name also derives (SELECT COUNT(*) FROM (SELECT 1 FROM items WHERE tenant_id = $1 AND name = $2 LIMIT 1) found); the hand-written method wins
```

**Searches (ADR 0027, in progress).** `nano gen repo` reads each `nanorepo.Search` of the package and checks it, and generates nothing for it yet. It reads the table instances the search reads, each a table and its alias: the table, or each table of the `From` function (one `return` of `table.X` joined with `INNER_JOIN` or `LEFT_JOIN`, or of a call of a function of the package that returns it), with the `ColumnTypes`, `ForeignKeys` and `UniqueKeys` that `nano gen db` writes, and the models. Every column of an option must be a column of an instance that the search reads, such as `table.Items.Name` or `table.Tenants.AS("owner").Name`, and so must every column of an expression function, or of the `FROM` of a subquery in it. Every column of a `LEFT JOIN` table is nullable in a result row, so the table of the search must not be on that side, and the join must start from the table of the search. The `ON` condition of each join reads only the tables before it and the joined table, and must equate every column of one unique key of the joined table that orders every row, with columns of the tables before it or with fields of the scope value: then the join adds at most one row per row, and the tiebreak and the count stay true. A field of the scope value counts only when it is read from the parameter of the `From` function, or from a parameter of a helper that gets that parameter itself; a constant or a package variable does not count. The scope value is a struct of plain values: a type that can hold a Nanostack DB value, such as an interface or a struct with an expression field, is refused. An alias matches `^[a-z_][a-z0-9_]{0,62}$` (PostgreSQL cuts a longer name to 63 bytes) and is not the name of a table of the table package. `RIGHT_JOIN`, `FULL_JOIN` and `CROSS_JOIN` are refused, because they bring rows that no tenant link reaches. A `From` or expression function can call only an allowlist: column and table references, `AS`, `INNER_JOIN`, `LEFT_JOIN`, the operators and functions that build an expression, `SELECT ... FROM ... WHERE` for a subquery, `Func` and `CAST(x).AS` with a constant SQL name, `DATE_TRUNC` with a constant time zone, the literal constructors, and the functions of the package. Anything else is refused, because it can hide SQL text or a table from the tenant check: `CustomExpression`, a `Token` conversion, `NewEnumValue`, the `Raw` constructors, `FromSchema`, `WithPrefix`, `WithSuffix`, a set operation such as `UNION`, a subquery `FROM` that is not a table variable or its `AS`, a package variable or a field whose type can hold a Nanostack DB value (a DB or table type, an interface, a function, or a struct, map or slice of them), a method value, a function literal, a call into another package. `VarChar(n)(x)` and `Char(n)(x)` are refused too: use `String(x)`. The tiebreak is the primary key in index order, unless `Tiebreak` names columns that contain every column of one unique key; a partial key, or a key with a column that can be NULL, does not count. A package with searches must also bind a repository with `nanorepo.Implement` or `nanorepo.Base`. `-explain` also prints each search, or those named:

```text
search ItemOptionalTenant on items (rows model.Items)
  from       itemsAndTheirTenant
  read       items; root; nullable weight, released_on, local_at, opens_at, deleted_at, external_id, tags; tenant tenant_id
  read       tenants; LEFT JOIN; ON table.Tenants.ID.EQ(table.Items.TenantID); one row by tenants_pkey (id); every column nullable
  filter     Name: Present on tenants.name (text, string)
  sort       name: tenants.name, nullable
  sort       created_at: items.created_at
  default    items.created_at ASC
  tiebreak   id: the primary key items_pkey (id), by default
search ItemOfNamedTenant on items (rows model.Items)
  from       itemsOfNamedTenant
  read       items; root; nullable weight, released_on, local_at, opens_at, deleted_at, external_id, tags; tenant tenant_id
  read       tenants; INNER JOIN; ON table.Tenants.Name.EQ(postgres.String(s.TenantName)); one row by tenants_name_key (name)
  subquery   SortExpr Siblings siblingCount reads items AS sibling; WHERE table.Items.AS("sibling").TenantID.EQ(table.Items.TenantID)
  sort       siblings: field Siblings = siblingCount()
  tiebreak   id: the primary key items_pkey (id), by default
```

The single run takes the scope columns from `-scopes`; the pipeline passes the `Postgres.Scopes` of the declaration, so `go tool nano gen -only repo` is the run to use in a service. The pipeline runs the step on each package that declares a repository, and reads the table code from Go source, never a database. The steps before repo load the package with a forward stub of each `<file>_repo.gen.go`: a method that panics for each interface method without a hand-written one, built by parsing alone. So the errors step still compiles a package whose interface just gained a method, or whose implementation just got a hand-written method that the last run derived. The methods of an interface of another package, or embedded from one, come from the last output on disk, minus those the implementation now has.

## The pipeline: `nano gen`

`nano gen` with no generator name runs every generation step of a module, in a fixed order: `db`, `api`, `validate`, `errors`, `repo`, `config`, `wire`. [ADR 0023](adr/0023-nano-gen-pipeline.md) records the design; package [`gen/pipeline`](../gen/pipeline) implements it.

```sh
go tool nano gen                 # run every step, write what changed
go tool nano gen -check          # write nothing; exit 1 listing every stale, missing or orphaned file
go tool nano gen -check -diff    # also print the first 20 lines of each diff
go tool nano gen -check -fresh   # CI: the db step ignores nanogen.sum and regenerates from the migrations
go tool nano gen -only config    # these steps, still in pipeline order (-skip is the inverse)
go tool nano gen -list           # print the plan: step, package, inputs, outputs
go tool nano gen -json           # one JSON event per line
go tool nano gen -dir apps/x     # the directory to run on; default: the module root
```

**The project declaration.** `nanogen/project.go` holds the inputs that nano cannot discover. It has no build tag, so `go build`, `go vet` and gopls type-check it, and nothing imports it. nano reads its composite literal from source, so every value must be a literal or a constant, and any other use of `Project` (an assignment in `init`, say) is an error. Paths are relative to the directory nano runs on. `API.Server.Dir` and `Postgres.Out` must stay inside that directory, because steps write there; `Env` may sit outside it. A declared `Env` with two `Config` packages is an error, since both would write it.

```go
// Package nanogen declares the inputs of this module's code generation that
// cannot be discovered. Run: go tool nano gen
package nanogen

import "github.com/nanostack-dev/nanostack-framework/core/nano/project"

var Project = project.Project{
	API: &project.OpenAPI{
		Spec:   "cmd/http/openapi.yaml",
		Server: project.Package{Dir: "internal/api"},
	},
	Postgres: &project.Postgres{Name: "anchor"},
	Env:      "../../.env.example", // default: .env.example next to Config
}
```

A module without the file still runs the steps nano discovers. `nano gen -list` then prints a declaration filled with the OpenAPI document and the server package it finds.

**Discovery.** nano parses the tree and never type-checks it, so discovery works on a tree that does not compile. It skips `testdata`, `vendor`, `node_modules`, hidden directories, directories that start with `_`, and nested modules, which run their own `nano gen`.

| Step | Runs on | Writes |
| --- | --- | --- |
| db | the `Postgres` of the declaration | the models and table types under `<Out>/<Name>/<Schema>`, and `<Out>/<Name>/nanogen.sum` |
| api | the `API` of the declaration | the server file (`api.gen.go`), `handlers.gen.go` next to it, and each client file (`client.gen.go`) |
| validate | the `API` of the declaration, when it has a server | `validate.gen.go` in the server package |
| errors | each package with a `//nano:errors` declaration | `errors.gen.go`, `ERRORS.md` |
| repo | each package that calls `nanorepo.Implement` or `nanorepo.Base`, with the `Postgres.Scopes` of the declaration | `repo_base.gen.go`, and `<file>_repo.gen.go` per file that calls `nanorepo.Implement` |
| config | each package with a `//go:build nanogen` file that calls `nano.Manifest` | `config.gen.go`, `CONFIG.md`, the `Env` file |
| wire | the same packages | `wire.gen.go`, in the manifest package |

**Order and failures.** Each step loads the fresh output of the steps before it. Without `-check`, a step writes before the next one loads. With `-check`, nothing is written: later loads see the fresh outputs as a `go/packages` overlay. In both modes, an existing output of a later step is replaced in each load by a stub whose function bodies panic, so a stale later output cannot break an earlier step. The repo step gives its derived files a forward stub instead: it declares the methods the next run will add, so an interface that just gained a method breaks no earlier step. A failed step skips the steps that need it (validate needs api; repo needs db; config needs validate, errors and repo; wire needs config), and the other steps still run. When db fails, repo is skipped and keeps its base; api, validate and errors load the models on disk, which are the last good ones. db, api, validate, repo and config read `nanogen/project.go`, so a declaration with an error skips them, and wire. A validation gap fails the run but skips nothing.

**Orphans.** Every output starts with `Code generated by nano gen <step>`. A file with that header, for a step that ran, that the run did not produce, is an orphan: `nano gen` deletes it and `-check` fails on it. So a deleted catalogue cannot leave its generated code behind, and neither can an `API` removed from the declaration. A skipped or failed step produced nothing, so its files stay. The db step plans `nanogen.sum` and the files it lists before it runs, and the files it produced after, so a run that hits its cache keeps the committed models and a dropped table's file is deleted. The scan does not run when a Go file fails to parse or holds an unknown `//nano:` directive: a misspelled `//nano:errors` would otherwise delete its catalogue's outputs.

**Guards.** An unknown `//nano:` directive is an error at its line. So is a `//go:generate` line that runs `nano gen` or oapi-codegen: the pipeline runs that step in its order. Delete the line and run `go tool nano gen`.

**Output.** A clean run prints nothing. Otherwise it prints one line per file (`wrote`, `deleted`, `stale`, `missing`, `orphan`), then each problem:

```text
stale cmd/app/config.gen.go
stale cmd/app/wire.gen.go
  fix: run nano gen without -check, then commit the result
greeterr/doc.go:3: unknown directive //nano:mapers
  fix: known directives are //nano:errors and //nano:error
nano gen wire: skipped: needs config
```

With `-json`, each event is one line on stdout: `{"step", "level", "file", "line", "msg", "fix"}`, plus `"diff"` with `-diff` and `"inputs"` and `"outputs"` with `-list`. `level` is one of `wrote`, `deleted`, `stale`, `missing`, `orphan`, `skipped`, `error`, `warning` and `plan`. A `warning` (the repo step's scope check) is printed as `warning: <file>:<line>: …` with its fix, and keeps exit 0. A problem found before any step runs, in the declaration, in discovery or by a guard, has the step `plan`.

## Running one generator

`nano gen <name>` runs one generator: `nano gen db`, `nano gen api`, `nano gen config`, `nano gen errors`, `nano gen repo`, `nano gen validate` or `nano gen wire`. Use it for a single run and in tests; the pipeline runs every step. `nano gen <name> -h` lists the flags of one generator.

`nano` and the generators are in the nested module `github.com/nanostack-dev/nanostack-framework/gen`, so their dependencies (`golang.org/x/tools` among them) stay out of the module graph of a service that only imports the runtime packages. A service pins `nano` with a `tool` directive and runs it with `go tool`:

```sh
go get -tool github.com/nanostack-dev/nanostack-framework/gen/cmd/nano@<gen tag>
go tool nano gen
```

The `gen` module requires the root module, so the framework's own root module cannot pin `nano` as a tool. It runs `go -C <path to gen> run ./cmd/nano gen -dir <directory>` instead: CI runs it with `-check` on [`internal/nanoexample`](../internal/nanoexample/doc.go) and on [`http/nanohttp/internal/example`](../http/nanohttp/internal/example/doc.go), whose `api.gen.go` and `handlers.gen.go` the api step writes. [RELEASING.md](../RELEASING.md#consumers-of-nano) gives the tag order.

Every generator, and the pipeline, takes `-check`: it writes nothing and exits 1 when a committed output is missing or differs from what the source produces. Run `nano gen -check` in CI next to the tests. Exit codes:

| Code | Meaning |
| --- | --- |
| 0 | Success. `-h` prints the flags and exits 0. |
| 1 | A source error, stale output, an orphan, or (for `validate`) a validation gap that no `x-nano-unenforced` accepts. |
| 2 | Bad usage. |
| 3 | The environment failed: the go command cannot load packages, a file cannot be read or written, the `nano` binary links another oapi-codegen than v2.8.2, or the db step needs a database and neither Docker nor `NANO_GEN_DATABASE_URL` gives one. |

Every error names its fix. A generator prints each error as its position and message, then an indented `fix:` line:

```text
config.go:15: Name: the field has no config tag
  fix: add a config:"name" tag, or config:"-" to skip the field
nano gen config: generated files are stale: config.gen.go
  fix: run nano gen config
```

An error with no file starts with `nano gen <name>:` instead of a position.

[Reviewing generated code](generated-code.md) shows what each generator writes and which parts of a generated diff to read by hand.

## Wiring: `nano gen wire`

`nano gen wire` replaces Fx. It reads a manifest, resolves the provider graph at generation time and writes plain Go: `wire.gen.go` with `Build` and `BuildComponents`. A missing provider, a cycle or a bad signature is a generation error with `file:line` and a fix, not a panic at boot. The runtime is [`core/nano`](../core/nano): the `App`, the lifecycle interfaces and `Main`. It uses no reflection.

### The manifest

A manifest is a package-level variable in a file with the `nanogen` build tag, so it never links into the service:

```go
//go:build nanogen

package billing

var App = nano.Manifest("billing",
	nanopg.Module,                      // a module variable from a library
	nano.Providers(invoice.NewService, invoice.NewPGStore),
	nano.Bind[invoice.Store, *invoice.PGStore](),
	nano.Collect[http.Handler](invoice.NewHandler, admin.NewHandler),
	nano.Invoke(RegisterMetrics),
)
```

| Entry | Meaning |
| --- | --- |
| `nano.Providers(fns...)` | Package-level constructors. Each provides its result type. |
| `nano.Module("name", items...)` | A named group of entries in ordinary code, so a library ships them as one value. |
| `nano.Bind[I, T]()` | Satisfies interface `I` with the provided `T`. Bindings are explicit: providing `*PGStore` does not satisfy `Store` by itself. |
| `nano.Collect[T](fns...)` | Provides `[]T`, one element per listed function, in declaration order across the manifest and its modules. Members do not provide their own type, so several may return the same type. `Collect[T]()` with no function declares an empty collection. |
| `nano.Invoke(fn)` | Calls `fn` after construction, in declaration order. `fn` returns nothing or `error`. |

Build also provides `context.Context` (Build's `ctx`), `*nano.App`, the manifest package's `Config` struct and each of its exported fields. A `nano.AppConfig` field of `Config` configures the App's timeouts.

Signature rules:

- A provider or collection member is `func(deps...) T`, `func(deps...) (T, error)` or `func(deps...) (T, func(), error)`. The `func()` is a cleanup that runs at stop, also when a later provider fails.
- Two providers of one type are an error. Two `Config` fields of one type are ambiguous to a consumer that takes that type.
- A provider whose type has a lifecycle method on the pointer receiver must return the pointer.
- In the manifest's own package, an unused provider, binding or collection is an error. In a library module it is skipped. There is no warning mode: the generator either writes code or fails.

### Lifecycle

A component opts in by implementing an interface. The generator sees it on the provider's result type and emits `app.Manage(name, v)` with a comment that names what it found:

| Interface | When the App calls it |
| --- | --- |
| `Starter` `Start(ctx) error` | Once, in dependency order, under `StartTimeout`. Work that can outlast it, such as database migrations, belongs in a `nano.Invoke` (see `pg/nanomigrate`). |
| `Stopper` `Stop(ctx) error` | Once, in reverse order, only if its `Start` succeeded (or it has none). |
| `Runner` `Run(ctx) error` | After every Starter, until `Stop` cancels `ctx`. Returning earlier shuts the App down and is an error. |
| `HealthChecker` `CheckHealth(ctx) error` | For `/readyz`. The name is specific so that an unrelated `Check` method is not a probe. |

`Manage` registers a component once. A provider that returns one of its dependencies as an interface (`func AsHandler(s *Server) Handler { return s }`) does not run or stop the server twice: the same pointer, or an equal comparable value, is skipped. A value whose static type is an interface gets its lifecycle from its dynamic type at run time.

Stop cancels the Runners, waits for them, then calls the Stoppers one at a time in reverse order. The drain and the Stoppers share `StopTimeout`. A Stopper called after that deadline still gets `nano.StopGrace` (one second), so a slow Runner or Stopper never cuts off a later flush. Stop returns within `StopTimeout` plus at most `StopGrace` per Stopper called after it. A Runner or Stopper that overruns is reported and left running.

`nano.Main` exits `0` after SIGINT or SIGTERM, also when the signal arrives during build (a migration or a ping returns the cancellation) or during start (`ErrShutdownDuringStart`) and every stop succeeds. It exits `1` on a build, start, Runner or stop failure, including a failure next to the cancellation. `AppConfig.DrainDelay` keeps the Runners serving for that long after readiness turns unavailable, so a load balancer stops routing to the instance before its listeners close; it is counted inside `StopTimeout`, and Start fails when it leaves the Runners less than `StopGrace` of it.

### Overrides and Components

Tests replace any provided value through the generated, typed `Overrides`. A nil field keeps the production provider. A set field skips that provider and every provider only it needed, and the App manages the override's lifecycle instead. Starters and Runners follow the same rule: a Starter or Runner that something takes is built only when a consumer that is built needs it, so overriding `Store` skips the real `*PGStore` and a pool that only it used, even when they ping on `Start`. A Starter or Runner that nothing takes is always built. A collection member is built only with its collection, so a Runner listed only in a `Collect` that nothing takes does not run (an error in the manifest's package, skipped in a library). Without overrides every value in the graph is built.

Override a collection as a whole: set the `[]T` field. A non-nil empty slice overrides it with no elements.

`BuildComponents(ctx, cfg, ov)` returns the App and a `Components` struct with a field per value (named like the `Overrides` fields; a collection member is named after its function). A field is named after its type (`*billing.Service` gives `Service`). When two values share a type name, both are qualified by their package name (`*nanopg.DB` and `*sql.DB` give `NanopgDB` and `SQLDB`). When their packages share a name too, each is qualified by its import path instead: by the fewest last path elements that no other of those paths ends with, a version element such as `v2` counting with the element before it (`example.com/billing/repository.Repository` and `example.com/invoice/repository.Repository` give `BillingRepositoryRepository` and `InvoiceRepositoryRepository`; with `example.com/eu/billing/store.Ledger`, `example.com/us/billing/store.Ledger` and `example.com/orders/store.Ledger`, the last one gives `OrdersStoreLedger`). Values whose names still collide, such as `*T` and `T` of one package, are numbered in the order of their full type names. A name depends on the set of provided types, never on their order: reordering providers renames nothing, and a new provider renames only the fields whose type name it shares. The generated variables follow the fields (`nanopgDB`, `needNanopgDB`). A slice of a name that ends in `s` gets `List` (`[]log.ContextAttrs` gives `ContextAttrsList`). A field holds the override when one was set, and the zero value when no built value needed it. This replaces `fx.Populate` in integration suites.

### Migrating from Fx

| Fx | Nanostack |
| --- | --- |
| `fx.Provide`, `fx.Module` | `nano.Providers`, `nano.Module` |
| `fx.Supply(v)` | A provider that returns `v`, or a `Config` field |
| `fx.Lifecycle` hooks | Implement `Starter`, `Stopper`, `Runner`; return a cleanup `func()` |
| `fx.Annotate(..., fx.As(new(I)))` | `nano.Bind[I, T]()` |
| Value groups, `fx.ResultTags(group)` | `nano.Collect[T](fns...)` in each contributing module; consumers take `[]T` |
| `fx.Invoke` | `nano.Invoke` |
| `fx.Populate(&targets...)` | `BuildComponents` and the `Components` fields |
| `fx.Replace`, and `fx.Decorate` in tests | A field of `Overrides` |
| `fx.Decorate` in production that returns the same value (for example it starts a listener on a client) | `nano.Invoke` with a function that takes the value |
| `fx.Decorate` in production that wraps the value | A provider of a distinct wrapper type, bound with `nano.Bind` where consumers take an interface |
| `fx.ValidateApp` | `nano gen -check` in CI |

### Commands

```text
nano gen wire [-dir .] [-out internal/gen/wire] [-tags a,b] [-check]
```

`-out` is relative to `-dir`; set it to `.` to generate into the manifest package. The pipeline always writes `wire.gen.go` into the manifest package. `-check` writes nothing and exits 1 when `wire.gen.go` is missing or stale. Output is deterministic. Generated provider errors read `nano: provide *T: pkg.NewT: <cause>`, without a source position, so moving a provider does not change the generated file.

Every generator follows the contract of package [`gen`](../gen/gen.go): `Options` with a `Check` field and an `Overlay` field, `Generate(Options) ([]gen.File, error)`, `Run(Options) error` (stale output wraps `gen.ErrStale`) and `Main(args, stdout, stderr) int`. `gen/validate` is the one variation: its `Generate` returns a `*Result` that holds the `gen.File` and the schema features it does not enforce.

- Every error is a `*gen.Error{File, Line, Msg, Fix}`, or several joined with `errors.Join`. A `Fix` is required: an error without one is a generator bug, and each generator's error table test fails on it. `gen.Errorf` takes the fix before the message.
- An error of the machine wraps `gen.ErrEnvironment`, and `Main` exits 3 on it.
- `Overlay` replaces files in every `go/packages` load, keyed by absolute path. The overlay never replaces a generator's own output: `config` loads a stub of it, `errors` and `validate` an empty file, and `wire` loads with `-tags=nanogen`, which drops `wire.gen.go`. A caller that keeps outputs in memory, such as a `-check` run of several generators, overlays the fresh outputs of the earlier ones. `api` loads no Go package, so its `Options` have no `Overlay`.
- `Main` prints with `gen.Report`. `Generate`, `Run` and `gen.Sync` add no `nano gen <name>:` prefix, and a Check run returns a `*gen.StaleError` that lists the stale files.

`gen/cmd/nano` routes `nano gen <name>` to each `Main`.

## Replacing Shell Scripts

Existing app scripts such as `generate_anchor.sh` and `generate_echopoint.sh` should be treated as migration sources. The framework path is:

1. Keep current scripts while framework generation is introduced.
2. Declare the generation inputs in `nanogen/project.go`; it replaces the oapi-codegen configuration files, `client-spec.sh` and `dbgen.go` (`Postgres`, with `Out` and `Name` at the current paths, so model imports do not change).
3. Add CLI commands that call visible tools and config files.
4. Switch app scripts to thin wrappers or remove them after `anchor` and `echopoint` validation passes.
