# 0024: The api step splits the strict server by OpenAPI tag

- Status: accepted
- Date: 2026-11-08

## Context

oapi-codegen's strict server has one interface, `StrictServerInterface`, with every operation. Anchor serves its 133 operations in 21 tags from one `AnchorAPI`, whose `NewAPI` takes 31 parameters, two of them unused. Echopoint serves 189 operations in 20 tags from 22 embedded feature handlers. Embedding gives silent shadowing, ambiguous selectors and promoted helpers. A handler gets every service of the API, so a dead dependency does not show.

The [pipeline design](../design/nano-gen-pipeline.md) (decisions T1 to T5, implementation plan PR 5) settles the split. This record covers it, and the points where the implementation refines the design.

## Decision

1. **The api step writes `handlers.gen.go` next to the server (T1).** It holds one `<Tag>Server` interface per tag, a `Handlers` type with one method per operation that passes the request to the handler of the operation's tag, `NewHandlers`, and `var _ StrictServerInterface = (*Handlers)(nil)`. `StrictServerInterface` does not change. The file starts with the `Code generated by nano gen api` header, so the orphan scan knows it. A tag name becomes a Go name through oapi-codegen's `ToCamelCase`: `Status pages` gives `StatusPagesServer`.
2. **A handler constructor returns its tag interface (T2).** `func NewEmailHandler(…) EmailServer`. A missing method is a compile error in the handler's own file. The manifest lists the constructors and `NewHandlers` in `nano.Providers`, with no `nano.Bind`.
3. **The tag rules (T3).** Every operation has exactly one tag. Every used tag is declared under the top-level `tags`, and every declared tag is used. No tag is declared twice. Each tag gives a Go name that starts with a letter, and two tags never give the same interface or the same `Handlers` field. A tag interface, `Handlers` and `NewHandlers` are not names the server already declares, such as a schema named `EmailServer`. Each problem is an error at the spec line that holds it, from kin-openapi's origins. A spec without tags fails: there is no default bucket.
4. **The rules apply to a server only.** A module that generates only clients, such as anchor's `clients/go`, checks no tag rule. Its spec's server, and its tags, live in another module, and a client does not split.
5. **The method names come from `codegen.OperationDefinitions` (T4).** `codegen.Generate` sets oapi-codegen's options in package state, and `OperationDefinitions` reads them. The step calls `OperationDefinitions` under the same lock, right after the server's `Generate` and before any client run. It reads a second copy of the spec: both calls rename the operations of the document they get, so the copy gives the names that `Generate` gave. A path that is a `$ref` to another path is an alias; oapi-codegen gives it no server method, so it has no handler method.
6. **`Handlers` fields are unexported (T5).** `NewHandlers` sets them once and refuses a nil handler: `NewHandlers: the handler of tag Email is nil`. Its parameters are sorted by interface name, so reordering the spec's `tags` list changes nothing. A field is the Go name with its leading capitals lowered (`APIKeys` gives `apiKeys`). A field that would be a Go keyword, or `checked`, the name of the nil check, gets a trailing underscore (`type_`, `checked_`), which no other tag produces: a field and a method of one type cannot share a name. The nil check is a method, so a parameter named after a tag cannot shadow a name the check uses.
7. **The pipeline names the missing method in full.** No step reported a compile error of a dependency: config and wire load the manifest package, and a handler package is one of its imports. wire now reports one class of dependency error: a type that lacks a method of a tag interface. The fix holds the method: `add the method of EmailServer: func (h *emailHandler) SendEmail(ctx context.Context, request SendEmailRequestObject) (SendEmailResponseObject, error)`. A method with the wrong signature gets `give SendEmail the signature of EmailServer:` and the same declaration. The receiver name is the one the type's other methods use. A handler in another package, such as an echopoint feature package, gets the server's types qualified by package name (`apigen.SendEmailRequestObject`), as its file writes them. Every other compile error of a dependency stays with go build. The same fix replaces the generic one on a root package's compile error.
8. **wire's fixes for a tag interface.** When no provider returns a tag interface, the fix names the provider to add, not a `nano.Bind`: `add a provider that returns api.EmailServer to nano.Providers in cmd/app/manifest.go`. A concrete provider type that implements the interface gets `make api.NewEmailHandler return api.EmailServer`. A provider type that has some of the interface's methods gets the first missing one, in full. `*Handlers` implements every tag interface by passing each call on, so it is never suggested. A `nano.Bind` whose type lacks a method gets the method in full in its fix too.

## Alternatives

- **One package per tag.** Shared schemas would become distinct types: 396 types instead of 253 in anchor, 588 instead of 403 in echopoint.
- **A fork of `strict-interface.tmpl`.** It is a third upstream template to compare on each upgrade.
- **Embedded handlers, as echopoint does today.** They give silent shadowing.
- **Embedded interfaces in `Handlers`.** A nil field panics at request time, not at startup.
- **An `x-nano-handler` extension.** It is a second grouping axis next to tags.
- **One `nano.Bind` per tag.** It adds 21 lines in anchor, and since `Bind[I, T any]` has no constraint, a missing method is a wire error at the Bind line, not a compile error in the handler.
- **A default bucket for untagged operations.** It hides a missing decision.
- **Several tags per operation.** A tag is now a code boundary.
- **Method names from the `// (METHOD /path)` comments of the server.** Fragile; the step already has the operations.
- **Exported `Handlers` fields.** A caller could set one to nil after the check.
- **Parameters in the spec's tag order.** The order of a list in the spec would change the constructor.
- **Every compile error of a dependency from wire.** A tree that does not compile yet, such as a caller of a mapper whose signature changed, would block wire, and go build reports those errors already. A missing tag method is the error the split creates, and its fix is mechanical.
- **Detecting a typed nil handler.** A nil pointer in an interface is not nil. A constructor that returns `&emailHandler{…}` never returns one, so the check stays `== nil`.

## Consequences

- Every spec with a server needs tags. The framework's fixtures and `http/nanohttp/internal/example` are tagged; their oapi-codegen output does not change, because oapi-codegen does not read tags without a tag filter.
- Anchor fixes 10 tag declarations (6 undeclared, 4 unused), then moves to the split in two steps ([design](../design/nano-gen-pipeline.md#worked-example-anchor)). Echopoint retags 8 tags that span several handlers before its split. Both happen in their own repositories after this release.
- A handler returns an interface, against Go's "return structs" habit. Its only consumer is `NewHandlers`. wire marks an interface-typed provider's lifecycle as dynamic; handlers have no Start or Stop.
- `handlers.gen.go` grows with the API, about 190 delegators in echopoint. It is generated, so its size costs nothing to maintain.
