# 0023: `nano gen` runs every generation step, in a fixed order, from one declaration

- Status: accepted
- Date: 2026-11-08

## Context

A service generates code in about 12 steps across docker, the `migrate` CLI, sed, `go generate`, `go run`, `nano gen` and pnpm. `nano gen` ran one generator per call. CI checked only some outputs. config and wire could block each other, and an agent had to delete files to recover. The roadmap asked for one command that runs every generator in order, but there was no file for its inputs.

The [pipeline design](../design/nano-gen-pipeline.md) (decisions P1 to P12) settles the whole feature. This record covers the pipeline core: its implementation plan, PR 3. The db, api, mapper and lint steps join it in later PRs.

## Decision

1. **`nano gen` with no generator name runs the pipeline.** It runs the steps validate, errors, config and wire, in that fixed order, one after another. `nano gen <name> -dir …` stays for single runs and tests.
2. **One typed declaration holds what cannot be discovered.** `nanogen/project.go` declares `var Project = project.Project{…}`. nano type-checks that one package, then reads the composite literal from the syntax tree, so every value is a literal or a constant. A function call or a variable is an error at its line. Today the declaration holds the OpenAPI document and its server package (`API`) and the `.env.example` path (`Env`).
3. **The declaration types live in the root module, at `core/nano/project`.** The design placed them in `gen/project`. But the root module never requires `gen`, and the framework's own example service, `internal/nanoexample`, sits in the root module and declares a project too. `go mod tidy` reads every build tag except `ignore`, so a tag cannot hide the import, and a declaration under `ignore` is type-checked by nothing, which defeats the point of the file. `core/nano` already holds the other declaration that a generator reads from source, `nano.Manifest`. The package is plain data and imports nothing. The reader stays in the `gen` module, in `gen/pipeline`.
4. **The rest is discovered by parsing, never by type-checking.** A `//nano:errors` declaration adds an errors unit. A package with a `//go:build nanogen` file that calls `nano.Manifest` adds a config unit and a wire unit. wire writes `wire.gen.go` into that package. The walk skips `testdata`, `vendor`, `node_modules`, hidden directories, directories that start with `_`, and nested modules.
5. **`-dir` names the directory the run covers.** The default is the module root. The framework runs the pipeline on `internal/nanoexample`, which is a package of the root module, not a module root.
6. **Generate writes after each step; `-check` writes nothing.** With `-check`, each later load gets the fresh outputs of the earlier steps as a `go/packages` overlay. In both modes, an existing output of a later step is replaced in every load by a stub: every function body becomes a panic, and an import that only the bodies used becomes a blank import. A stale later output then cannot break an earlier step.
7. **A failed step skips only the steps that need it.** config needs validate and errors. wire needs config. validate and config read `nanogen/project.go`, so a declaration with an error skips them, and wire. Otherwise a broken declaration would write the `Env` file to its default path and delete the declared one as an orphan. A validation gap fails the run (exit 1) but skips nothing, because its file is still written.
8. **Orphans come from headers.** Every output starts with `Code generated by nano gen <step>`. A file under the run's directory with that header, for a step that ran, that the run did not produce, is an orphan. Generate deletes it. `-check` fails on it. A step with nothing to run on has run: errors without a catalogue, and validate when the declaration has no `API`. A skipped step has not run, and validate has not run in a module without `nanogen/project.go`. The scan does not run when a Go file fails to parse, because a declaration in that file could be missing.
9. **Two guards.** An unknown `//nano:` directive is an error at its line. A `//go:generate` line that runs `nano gen` is an error at its line.
10. **Validate waivers move into the spec.** `x-nano-unenforced: "<reason>"` on a schema accepts the gaps of that schema and of every schema under it. The reason may not be empty. An extension that accepts no gap is an error, so it cannot hide the next gap. The `-allow` flag and `Options.Allow` are removed.
11. **Output for agents.** A clean run prints nothing. Otherwise it prints one line per file (`wrote`, `deleted`, `stale`, `missing`, `orphan`), then each problem as `file:line: msg` with an indented `fix:` line. `-json` prints one event per line: `{step, level, file, line, msg, fix}`, plus `diff` with `-diff`, and `inputs` and `outputs` with `-list`. `-only` and `-skip` select steps, still in pipeline order. Exit codes are 0, 1 (source error, gap, stale, missing or orphan), 2 (usage) and 3 (environment).

## Alternatives

- **`go generate`.** It has no order and no check, and it would also run generators that the pipeline must not run, such as network-bound ones.
- **`nano.yaml`, as buf and sqlc do.** It has no compiler, no rename support, and it is a second schema to learn.
- **Markers only.** A spec path in a comment is untyped, and inputs such as the DB image still need a home.
- **`go run ./nanogen`.** It needs a second binary and a cold compile on every run.
- **Declared membership lists.** A package would be listed twice, so an agent makes two edits.
- **The declaration types in `gen/project`, as the design says.** The root module would require `gen` for its example service, or that service would need its own module with four `replace` lines. Rejected for the layering rule.
- **A nested module for `internal/nanoexample`.** It keeps the design's import path, but it adds a module that the release checks do not know. The pipeline would also read a declaration from one module and generate another.
- **Steps in parallel.** wire type-checks the outputs of every earlier step.
- **Everything in memory until the end.** An overlay cannot add a whole new directory, such as a fresh DB tree.
- **An `outputs.txt` manifest or a lock file for orphans.** It churns on every change and restates what the header already says.
- **Stop at the first failure.** An agent needs every fix from one run.
- **Silently ignore an unknown directive.** A misspelled marker would drop a step.

## Consequences

- The framework CI runs `nano gen -check` on `internal/nanoexample`. Its `//go:generate` lines are gone, because the guard rejects them.
- A service adopts the pipeline with `nanogen/project.go` and `go tool nano gen -check` in CI. It deletes its `//go:generate` lines for `nano gen` and its `Run(Check)` tests.
- The guard does not yet reject a `//go:generate` line that runs oapi-codegen (P12). Until the api step (design PR 4) generates the server, that line is the only way to regenerate it. The api step adds the check.
- `-fresh` and exit 3 for Docker belong to the db step (design PR 6).
- A `-list` run without `nanogen/project.go` prints a declaration filled with the OpenAPI document and the server package it finds.
- A stub guesses the name of an import without an explicit name from its path. When the guess finds no use, the stub keeps the import as it is.
