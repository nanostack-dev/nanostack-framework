# 0026: `nano gen repo` binds one repository interface to a go-jet table, on a generated base

- Status: accepted
- Date: 2026-11-08

## Context

A Nanostack repository is an interface, an implementation struct and hand-written go-jet code. Each finder passes the database and the mapper to a `pkg/db/transactor` function, writes the same `WHERE tenant = $1 AND id = $2` and the same `LIMIT 1`, and repeats the no-rows handling. Anchor's product-user and platform-user repositories hold nine such methods in 156 lines. A `LIMIT 1` on columns that are not unique returns whichever row PostgreSQL reads first, and nothing reports it.

The user's rule for part 1 (2026-11-08): "spring data like method following a standard that generate code if the method is not handmade; if the interface has a method he can't generate and found no implementation we fail in build." A raw-SQL directive (`//nano:query`) is dropped: go-jet stays the one way to write SQL. The design (`reports/design-repo.md` in the workspace, decisions D1 to D27) was prototyped on anchor's code: 55 database tests compare the derived methods with anchor's own.

The design ships in three PRs: the db step with `UniqueKeys()` (PR 6, [decision log](../decision-log.md#2026-11-08-nano-gen-db-writes-the-models-uniquekeys-and-nanogensum)), the base (PR 7) and the derived methods (PR 8). This record covers both.

## Decision

1. **One declaration binds an interface to its implementation and a table (D2, D3).** `nanorepo.Implement[Iface, impl](table.X, toDomain)` inside `func _() { … }`, in a file without a build tag, so the compiler, `go vet` and gopls check it and a rename updates it. The model row and the domain type come from `toDomain`. `nanorepo.NoMapper[model.X]` returns the model rows; `nanorepo.Base[model.X](table.X)` declares a base with no interface.
2. **The declarations live in `db/nanorepo` (D4).** It imports only the standard library, and its functions do nothing at run time. The root module never requires `gen`, and a service imports the declarations, so they cannot live in `gen`.
3. **Each table a declaration names gets a generated base (D15).** `repo_base.gen.go` in the declaring package holds, per table, `<table>Base` with the table (`t`), typed predicates (`where`), helpers that take a condition (`findOne`, `first`, `findAll`, `exists`, `count`, `deleteWhere`, `updateWhere`) and every `pkg/db/transactor` function as a method, generic where the function is (`query[T]`, `queryOptional[T]`, `queryMap`, `queryOptionalMap`, `queryMapSlice`, `queryCount`, `exec`, `execAffected`, `page`, and `queryRow`, `queryRowOptional`, `queryRows`, which map with the declaration's mapper). The implementation embeds the base and sets it with `new<Table>Base(db)`.
4. **No silent first row (D16, D17).** `findOne` reads `LIMIT 2` and returns `transactor.ErrMoreThanOneRow`, wrapped with the table name, when two rows match. `first` takes at least one order. The sentinel lives once, in `pkg/db/transactor`, so `errors.Is` matches across repository packages.
5. **Every helper runs through `pkg/db/transactor` (D18).** The context transaction and the row-lock rules hold: `findOne`, `first` and `findAll` honour `transactor.ForUpdate`; PostgreSQL refuses a lock on `exists` and `count`, which aggregate; `deleteWhere` and `updateWhere` run through the new `transactor.ExecAffected`, which refuses a lock as `Exec` does and returns the affected rows. A nil condition on a write is an error, not a write to every row.
6. **The mapper takes no state (D5, D6).** It is a function, or a variable of the declaring package set to a function, a function literal or a method value on a type without fields. A method value on a type with fields is an error: the base calls the mapper with no dependencies. Two declarations on one table in one package share its base, so they pass the same mapper and read the same model.
7. **PostgreSQL only in part 1 (D20).** A declaration on a MySQL or SQLite table is an error whose fix is to remove it; the repository stays hand-written.
8. **The scope columns come from the project file (D25, D26).** `Postgres.Scopes` names the tenant columns. A table is scoped when it has one as a `NOT NULL` column. A hand-written function that touches a scoped table through its base (a predicate, a helper, a `SELECT`, `UPDATE` or `DELETE` on `b.t`, or a `SELECT` that reads `FROM` `b.t` or a join on it) without a predicate or a reference on a scope column gets a warning, unless its name ends in `Internal`. Warnings keep exit 0 and reach `-json` as `warning` events. A derived name must filter on a scope column first; a name that ends in `Internal` skips the rule on a read only, and is marked `UNSCOPED`. A delete across tenants never derives: it is hand-written, where review sees it.
9. **The output is all or nothing (D13, D27).** The generator loads the package with every file it wrote replaced by an empty file, so a stale output never blocks a run, then type-checks the package with the new files. A compile error that remains is reported at its line, beside every method that does not resolve, and nothing is written.
10. **The repo step runs after errors and before config, and needs db (D27).** It reads the table code and its `UniqueKeys()` from Go source, never a database, so `-only repo` and `-skip db` run without Docker. A failed db step skips it, and config needs it. `-list` shows one unit per declaring package.
11. **Each interface method resolves hand-written, then derived, then fails (D8 to D12).** A method of the implementation in a file without the nano gen repo header, or one promoted from an embedded field (each field looked up on its own, the shallowest wins, two at one depth are an error), wins, and its signature must be identical to the interface's. A method a previous run generated never counts, so a newly embedded helper wins over a stale derived copy. Otherwise the name derives, or the run fails at the interface method with the signature to paste and a derivable rename when one works. Methods of embedded interfaces resolve the same way, from any file another tool wrote.
12. **The grammar is equality on named columns (D21 to D23).** `FindBy`, `GetBy`, `ExistsBy`, `CountBy`, `DeleteBy`, `FindAll`, `Count`; Go field names joined by `And`; `ctx` first, then one parameter per column bound by position, of the model type or a named type over it, never a pointer, never named after another column of the name. The results are fixed per prefix. Operators, `OrderBy` and `Or` do not derive; the error gives the hand-written body.
13. **A single-row find is proven unique (D24).** It derives only when its columns cover the primary key or a key that the db step lists in `UniqueKeys()`, read with `go/parser`. A table package without `UniqueKeys` is an error whose fix is `nano gen db`.
14. **One `<file>_repo.gen.go` per declaring file, with a backstop (D7, D14).** It holds the derived methods of the file's bindings and a `var _ Iface = (*impl)(nil)` line each, so a deleted hand-written body fails `go build` before the next run. The bases stay in `repo_base.gen.go`. A derived file whose binding is gone is an orphan.
15. **The steps before repo see a forward stub (D27).** Built by parsing alone, it declares a panicking method for every bound interface method without a hand-written one, so the errors step still compiles a package whose interface just gained a method. `nano gen repo -explain [Iface…]` prints the resolution of each method and needs no database.

## Alternatives

- **`//nano:query` with SQL text.** Dropped by the user: it removes the purpose of go-jet, and it needed a database, plan analysis and a new executor in the repo step.
- **A `//nano:repo impl=… table=…` comment.** It is untyped, and a rename does not update it.
- **Naming conventions** (`XRepository` → `xRepositoryImpl`). Anchor's `resourcetype` uses `Repository` → `repositoryImpl`.
- **Hand-written methods that pass `r.db` and the mapper to transactor functions**, as anchor does. Each finder repeats both.
- **`LIMIT 1` in `findOne`.** It hides a missing unique key.
- **One `ErrMoreThanOneRow` per generated package.** `errors.Is` across two repository packages would not match.
- **Package-level generic functions that take the base**, instead of generic methods. Each call repeats the base.
- **Any method value as a mapper.** A zero-value mapper with state panics: anchor's `IntegrationInstanceMapper.ToDomain` calls its cipher.
- **`nanorepo.Scope` per declaration**, as the prototype had. A declaration can leave it out.
- **The scope check as an error now.** Anchor's hand-written finders need a review first; it becomes an error once anchor's `Internal` methods are clean.
- **Partial output on error.** A base written while another declaration fails would leave the package half generated; the tree keeps the last good files.
- **Derived before hand-written.** The user asked to generate a method "if the method is not handmade"; a hand-written case-insensitive `ExistsByProductIDAndEmail` must win over the derived equality.
- **Skip every file with a "Code generated" header**, or every `.gen.go` file, when looking for hand-written methods. A method another generator wrote exists at compile time; a generated duplicate would not compile.
- **Binding by parameter name** (`:name`), or by position alone. Names existed to bind SQL text, which is gone; position alone let `ExistsByProductIDAndExternalID(ctx, externalID, productID)` filter the tenant on the external ID.
- **`LIMIT 1` for a single-row find with no key.** It returned whichever row PostgreSQL read first.
- **One `repo.gen.go` per package**, as the prototype had. Parallel pull requests would conflict in one large file.
- **The body-stripped stub for the derived files.** It keeps the last `var _` line and cannot add the method an interface just gained.
- **`Internal` on derived writes.** A scope-free delete is too easy to derive by a rename; it stays hand-written.

## Consequences

- A service declares `Postgres.Scopes`, embeds a base per table, deletes the bodies that derive and moves the rest onto `r.findOne`, `r.first` and `r.where`, one repository file at a time. Every hand-written `LIMIT 1` on columns that are not unique moves to `first` with an order. A derived name says every column it filters on, so finders whose names hide a filter are renamed, with their call sites.
- The base needs Go 1.27 for its generic methods. Go 1.27.0 to 1.27.3 lose the order of generic methods in export data (golang/go#81188), so a service that adopts the base keeps the framework's `TEMP(golang/go#81188)` lint exceptions until Go 1.27.4 ([decision log](../decision-log.md)).
- String predicates compare as text (`$1::text`). On a column of another type that the model reads as a string, such as `json`, `inet` or `tsvector`, the predicate fails at run time; such a column is compared on `b.t`. Enum columns cast to their type, so their index applies.
- The single run takes the scope columns from `-scopes`; services run `go tool nano gen`, which passes `Postgres.Scopes`, and its `-check` catches a derived name the scope rule refuses.
- Parsing cannot list the methods of an interface of another package, or embedded from one: the forward stub takes them from the last output on disk, minus those the implementation now has, so until repo runs an earlier step sees them as the last run left them.

## Amendment, 2026-11-09: short scope names and context scopes in derived names

Derived names read badly on a table with several tenant columns: `FindByID(ctx, organizationID, id)` was hand-written because `FindByOrganizationIDAndWorkspaceIDAndID` does not read, and a derived read ignored `Postgres.ContextScopes`, which only searches applied (ADR 0027). This amendment changes D25's rule for derived methods only.

- **`Postgres.ScopeNames`** maps a scope column to a short Go name (`organization_id` to `Org`). In a derived name a short name is a word that resolves to that column, beside the Go fields, which keep deriving. Words match longest first, so the field `ProductID` beats the short name `Product`. The project check requires each key in `Scopes`, each value an exported identifier and no name on two columns; the run refuses a short name that is the Go field of a different column of a table.
- **A context scope named by its short name binds no parameter.** The method ANDs the registered function: `workspacescope.Filter(ctx, r.t.WorkspaceID)`. Its Go field keeps an explicit parameter and plain equality.
- **A derived read or delete on a table with a context scope column must name it**, in either form, nullable or not. The registered function returns TRUE when the request carries no workspace, so it is safe on a nullable column. A read may end in `Internal` instead, which skips the context scope and is marked `UNSCOPED`. A delete has no escape, as before. The first word must still be a scope column; a context scope satisfies that only when it is the table's one scope.

Alternatives rejected:

- **Apply the context scope to every derived method silently.** The name would hide a filter, which D25 and the derived grammar forbid: a derived name says every column it filters on.
- **Make the short name bind a parameter and ignore the function.** The caller would pass the workspace by hand, which a request-context scope exists to prevent.
- **Allow a delete with `Internal`.** A scope-free write stays hand-written, where review sees it.

Consequence: a service that declares a context scope must rename or hand-write each derived method on the table that does not name it; the refusal gives the rename. See [Derived names and tenant scopes](../generated-code.md#derived-names-and-tenant-scopes).

## Amendment, 2026-11-09: derived writes

Decision 12 derived reads and `DeleteBy` only: echopoint wrote 34 write methods by hand and anchor 58, most of them an `INSERT ... RETURNING` of every column or an `UPDATE` of every column by scope and id. Decision 6 gave a declaration one direction, row to domain, and a write needs the other. This amendment adds writes to the grammar.

- **`nanorepo.ToRow(toRow)`, an option of `Implement`.** `Implement[I, Impl, E, D](table, toDomain, options ...Option)`. `toRow` maps `D` to `E` and follows the stateless rule of `toDomain` (decision 6). `Option` is not generic, because `OnUnique` cannot infer `E` and `D`; the run checks that `ToRow` maps the types of `toDomain`. A declaration with `NoMapper` needs no `ToRow`: its writes take the model.
- **`nanorepo.OnUnique(target, constraint, more...)`.** Every derived write of the declaration returns `target` on a unique violation of one of the constraints, through `transactor.Result.OnUnique`. `target` is a package-level error variable. Each constraint is a string constant that the table file lists: a key of `UniqueKeys()` or a "Not a key" index of its doc comment (an expression or partial index), so `nanostack gen db` needs no new method.
- **`Create(ctx, x)` and `CreateIn<Scope...>(ctx, scopes..., x)`.** An `INSERT` of every column except `Postgres.DatabaseColumns`, read back with `RETURNING`. On a scoped table the name is `CreateIn` with the write scope rule below. A hard scope binds a parameter that overwrites the column of the value, so a value that names another tenant still lands in the caller's. A context scope named by its short name is set from the new `ContextScope.Stamp` function (`workspacescope.Stamp`), whose error the method returns; a request without a workspace creates nothing. `CreateIn` names scope columns only.
- **`UpdateBy<Scope...>And<Key...>(ctx, scopes..., x)`.** The write scope rule below. Scope words bind parameters; context scopes apply their function; the other words are key columns read from the value. The key columns and the hard scopes, not the context scopes (whose function can read TRUE), cover the primary key or a key of `UniqueKeys()`. `SET` holds every column except the name, every scope column, the primary key and the database columns, so an update never moves a row to another tenant. No row is `sql.ErrNoRows`, or an absent `Option`. A request without a workspace updates in its whole tenant, as a read does.
- **`UpsertBy<Scope...>And<Key...>(ctx, scopes..., x)`.** It conflicts on one key that holds a hard scope (below), so a conflict cannot reach a row of another tenant. `DO UPDATE` sets the columns an update sets, and only when the existing row has the caller's value of every scope column outside the key (`WHERE t.workspace_id = EXCLUDED.workspace_id`): an upsert that meets a row of another tenant or workspace changes nothing and returns `sql.ErrNoRows`.
- **`Postgres.DatabaseColumns`**, such as `created_at` and `updated_at`: the database writes them (a default, a trigger). Derived writes never set them and read them back. A Create or an Upsert on a table where such a column has no default is refused.
- **The write scope rule, stricter than the read one: no scope column comes from the value.** In a project with `Postgres.Scopes`, the table of a derived write has a NOT NULL hard scope and no nullable scope column, and the name names every scope column of the table: each hard scope binds a parameter, each context scope is its short name (stamped on an insert, its function on an update). A table with no scope column, with a context scope only, or with a nullable scope (rows that no tenant or every tenant owns) gets no derived write. A read needs one hard scope because it only narrows; a write that left a second hard scope to the value would write it.
- **An upsert's conflict key** is the one unique key, not partial, among the name's columns that holds every key column of the value and a hard scope. Every scope column outside the key guards `DO UPDATE` with the caller's parameter or stamp.
- **Writes never end in `Internal`**, as decided for deletes. A partial update, a write of an input type that is not the domain type, a write of two tables and an optimistic lock stay hand-written, on `r.updateWhere` and the hatches.

Alternatives rejected:

- **A generic `Option[E, D]`.** It checks `ToRow` at compile time, but `OnUnique` cannot infer its type arguments, so each call would spell them.
- **A variadic `toRow ...func(D) E` after `toDomain`.** Type-checked, but it takes the only variadic slot, and `OnUnique` needs one.
- **`Create(ctx, x)` on a scoped table, with the tenant from the value.** The value often comes from a request body; the parameter comes from the authenticated principal, as for reads.
- **The key of an update as a parameter (`UpdateByOrgAndID(ctx, orgID, id, x)`).** The id would be passed twice and could disagree with the value.
- **An upsert key without the scope, guarded in `DO UPDATE`.** The guard would turn another tenant's row into an error on a plain insert path, and the key would still tell the caller that the slug exists in another tenant.
- **Writing a database column when the value sets it.** A zero time would be written where the database should; a column the database owns is never written.
- **A `UniqueIndexes()` method from `nanostack gen db` to check `OnUnique`.** The "Not a key" lines already list every other unique index with its reason; a method would regenerate every table file for no new fact.

- **Writes on a table without a hard scope, or with only the first hard scope named.** A review of the first draft derived `CreateInWorkspaceID` with the tenant from the value, `UpdateByID` on a table whose only scope was nullable, and `UpdateByWorkspaceAndID` across every tenant when the request had no workspace.

Consequence: a service declares `ToRow` (and `OnUnique` where it maps a duplicate), `DatabaseColumns` and `ContextScope.Stamp`, renames its writes into the grammar, passes the scope from the principal at each call site, and deletes the bodies. The derived bodies drop hand-written log lines and error wrapping; the sentinels stay. A write's name holds every scope of its table, so a table under three hard scopes reads `UpdateByTenantAndProductAndOrgAndID`. `updated_at` in `DatabaseColumns` needs an update trigger, which the run does not check. A Create whose value carries the id of another tenant's row fails on the primary key, as a hand-written insert does. See [Derived writes](../generated-code.md#derived-writes).

## Amendment, 2026-11-10: every scope column, and no derived method on a view

A review with a torture fixture on PostgreSQL (the `gen/repo/internal/torture` tests) found that the rule "the name starts with a scope column" let a derived method omit a tenant filter. On a table with `org_id`, `product_id` and `site_id`, `FindByOrgAndName` read every product of the org; `DeleteByWorkspaceIDAndSeq` on a table scoped by an org, a product, a site and a workspace deleted rows of every org; a nullable `Scopes` column was no scope at all; `DeleteByID` on an updatable view deleted any tenant's row. This amendment changes D25 for derived methods.

- **A derived name gives every column of `Postgres.Scopes` of its table**, hard or context, `NOT NULL` or nullable, scope words first and in any order among themselves. A nullable hard scope is named with equality, so a row with no value matches no name. A read may end in `Internal`, which skips the missing columns and is marked `UNSCOPED`; a delete has no escape. A context scope in either form satisfies the rule only for its own column.
- **`Postgres.ScopeImplies`** maps a column to the column it determines (`{"product_id": "platform_tenant_id"}`), applied transitively, **per table and only where the table proves it**: an entry applies on a table only when that table proves it: a foreign key of the table lists both columns among its referencing columns, and the referenced table has a unique key on the column that the first one references, alone (`FOREIGN KEY (product_id, platform_tenant_id) REFERENCES products (id, platform_tenant_id)` with `products.id` unique, all its referencing columns NOT NULL (or MATCH FULL), and the key validated, proves `product_id -> platform_tenant_id`). Without the proof the implication does not apply to that table and the refusal names the missing foreign key. A write never uses an implication: it names every scope column. Both sides are in `Scopes`, neither is a context column, and there is no cycle; the pipeline and the `-scope-implies` flag check it with one function. The first version applied the map to every table, and the torture fixture showed that a table where every product appears under two orgs derived `FindByProductAndName` with no `org_id`. Searches already cover every tenant column, so the two rules agree.
- **The Go field of a context scope (`WorkspaceID`) is allowed on reads only**: a deliberate cross-workspace read with an explicit parameter, and the generated comment says `CROSS-WORKSPACE`. A derived delete or write that names it is refused: a cross-workspace change is hand-written, where review sees it. `nanostack gen repo -inventory` lists every `UNSCOPED` and `CROSS-` method for review.
- **`ContextScope.Present`** (`func(context.Context) bool`, optional) and **`ContextScope.AllowFailOpenWrites`** (bool). A registered filter reads TRUE when the context carries no value, which is right for an organisation-wide read on a table that has a hard scope, and wrong where nothing else scopes the statement. Three rules follow. (1) A derived delete or update on a table with a context scope must either find the value in `ctx` (`Present` set: the method first checks it and returns `nanorepo.ErrNoContextScope` before any SQL; creates and upserts check it too, and their stamp fails without a value anyway) or record a reviewed choice (`AllowFailOpenWrites`: the generated comment says `FAIL-OPEN (reviewed)` and `-inventory` lists the method). Otherwise the method is refused: a warning was rejected, because a warning is read once and a fail-open delete is a data-loss bug. (2) A derived read of a table whose only scopes are context scopes (`note`, `draft`: no hard scope) must also be fail-closed: with `Present` it checks it; without, it is refused unless the name leaves the scope out and ends in `Internal`, or binds the column from a parameter (the `WorkspaceID` form); `Internal` exempts only the scopes the name skips, so a fully named read still needs `Present`. A table that has a hard scope keeps the fail-open read: an organisation-wide read is intended. (3) The sentinel is in `db/nanorepo`, the declarative layer that generated code already imports, not in the legacy `transactor`. Echopoint keeps its fail-open behaviour for the hand-written code it has today; a derived write there needs `Present` (an organisation-level API key then needs a workspace) or `AllowFailOpenWrites` (an org-level key may act without the header: the behaviour of today).
- **`nanostack gen repo -verify-scopes`, and the same check inside every `nanostack gen` and `-check` run.** It reads the derived code and takes each table's scope columns from its generated table package. A read or delete covers a scope column only by a **conjunct of the condition of its top-level statement** (`r.where.F(x)`, the registered function on the column, or a proven implication): an `OR` or a `NOT` around a predicate covers nothing. A create stamps each column, an update has each in its WHERE, an upsert stamps each and has each in its conflict target or DO UPDATE guard. A delete, a write, and a read of a context-only table must call the registered `Present`, matched by import path and name, not by identifier. Only the condition of the top-level statement credits a scope (not a nested SELECT or helper), and a context function credits its column only when it is the registered one. `-inventory` lists every `UNSCOPED`, `CROSS-`, `ORG-WIDE (ctx scope fail-open read)`, `FAIL-OPEN (reviewed)` method, and every hand-written method whose name also derives (`HAND-WRITTEN (derivable)`), which the check cannot read.
- **A derived method on a view is refused**: `nanostack gen db` types every view column as nullable, so no view column is trusted as a scope. Hand-write it with the filter in its condition, or bind the base table.
- **A parameter whose named type says another column of the table** (`ProductID` for `org_id`) is refused.

Alternatives rejected: keep "starts with a scope column" and rely on review of the name (the omission is invisible in a name that reads well); derive `ScopeImplies` from foreign keys alone (a foreign key that does not reference a unique key of the first column says nothing about it, a key with a nullable referencing column under MATCH SIMPLE skips the check on a row with a NULL, a NOT VALID key leaves the rows that predate it unchecked, and a table that has no foreign key proves nothing: the declaration says what is meant, the foreign key proves it per table); apply the map to every table (unsound, as the first version showed).

Consequence, breaking: a service that has a table with more than one scope column, a nullable scope column, or a derived method on a view must, after `go tool nanostack gen`, rename each refused method (the refusal gives the name and the parameters to add), declare `ScopeImplies` where the schema guarantees it (the table needs the foreign key that proves it), set `ContextScope.Present`, or hand-write the method.
