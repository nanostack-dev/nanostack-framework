## Rules for the fork

1. **Rename identity, not structure.** The only mechanical change to upstream files is the
   module path (`github.com/go-jet/jet/v2` → `github.com/nanostack-dev/nanostack-framework/db`)
   and the modification header. Package names, file names and internal layout stay the same,
   so an upstream diff stays readable.
2. **Every file taken from go-jet keeps a header** saying it was modified (Apache-2.0 §4(b)):
   `// Modified by Nanostack from go-jet (https://github.com/go-jet/jet), commit d0e152c.`
3. **New Nanostack code lives in new files** where possible, so upstream merges rarely conflict.
4. **Send generic fixes upstream.** A bug that is not Nanostack-specific goes to go-jet as a PR too.
5. **All dialects stay supported.** A change that touches shared code passes the PostgreSQL,
   CockroachDB, MySQL, MariaDB and SQLite suites before it merges.

## Merging an upstream release

`tools/upstreamsync` does the mechanical part. From `db/`:

```sh
go run ./tools/upstreamsync -ref <tag-or-sha> [-stat] [-apply]
```

It keeps a bare mirror of go-jet in the user cache directory (`-cache` to move it, `-upstream`
for another URL, `-repo <clone>` to use an existing full clone without fetching). It exports
the Base commit and the ref with `git archive`, applies the import rewrite (module path, and the
two-line header on every `.go` file) and prints:

1. **Upstream changes**: base → ref, after the rewrite. Header lines never show here.
2. **Nanostack changes**: rewritten base → `db/`, for files that exist upstream. Files that only
   Nanostack has (`UPSTREAM.md`, `README.md`, `tools/`, new Nanostack files) and `tests/.gentestdata/`
   are left out. Upstream `README.md` is compared with `docs/upstream/README.md`, where the fork
   keeps it. A deleted upstream file shows as a deletion.
3. With `-apply`: a 3-way merge per file (`git merge-file`, ours = `db/`, base = rewritten Base,
   theirs = rewritten ref with the ref's commit in the header). It lists `updated` (ours was
   unchanged, upstream content changed), `merged` (clean), `added`, `deleted` and `CONFLICT` lines, plus a count of files whose only change is the header commit. A text conflict leaves
   markers labelled `Nanostack DB` / `upstream base` / `upstream ref` in the file. A file deleted
   on one side and changed on the other is never deleted or restored: the tool keeps our side and
   lists it, except for the `dropped` paths (CI and GitHub configuration of go-jet's
   repository), which it lists as `dropped`.

Before the sections it prints an `IGNORED` line for each upstream file that git ignores in
`db/` (a commit would drop it; add a `.gitignore` negation), and counts them as conflicts.

It also prints the upstream `tests/testdata` submodule pin (the jet-test-data commit) for both
sides. When the pin moved, `-apply` rewrites `TestDataCommit` in
`tests/internal/testenv/testdata.go`, the commit the harness fetches. Exit status: 0 = no
conflicts, 1 = conflicts (or ignored upstream files), 2 = error. `-base <ref>` overrides the Base
commit, to review any upstream range.

Procedure:

1. Find the release: `git ls-remote --tags https://github.com/go-jet/jet.git 'v2.*'`.
2. Review it without changing anything:
   `go run ./tools/upstreamsync -ref vX.Y.Z > /tmp/jet-vX.Y.Z.diff`. Read section 1 (what
   upstream changed) next to section 2 (what we changed). Check the "Changes from upstream"
   table: a row whose change is now in upstream is removed after the merge.
3. In a clean worktree on a new branch (`chore/db-go-jet-vX.Y.Z`), run
   `go run ./tools/upstreamsync -ref vX.Y.Z -apply`. Git is the undo: `-apply` only writes
   files under `db/`.
4. Resolve every `CONFLICT` line. For a text conflict, edit the markers away and keep the
   Nanostack behaviour unless upstream now does the same thing. For a modify/delete conflict,
   decide by hand and record the decision in the changes table.
5. Update the Base table: the full commit SHA, the release, the commit date
   (`git -C <mirror> log -1 --format=%cs vX.Y.Z`) and, if the pin moved, the Test data row
   and the commit in `tests/Readme.md` (`-apply` already set `TestDataCommit`; the sync
   tool's tests fail until all three agree). Update `upstreamCommit` in
   `cmd/jet/nanostack_version.go` (its test compares it with the Base commit).
   The headers already name the new commit (the merge carried them), so until the Base row is
   updated, section 2 shows every Go file as changed: that is the signal the table is stale.
6. Rerun `go run ./tools/upstreamsync -ref vX.Y.Z -stat`. Section 1 must print `(none)`.
   Section 2 must list only the files of the changes table.
7. `go mod tidy` in `db/` and `db/tests/`; keep `go 1.27`. In `db/go.mod`, move the test
   dependencies back to go-jet's `// used in tests` block, which tidy joins to the first one. Then
   `grep -rn 'github.com/go-jet/jet/v2' --include='*.go' --include='go.mod' --exclude-dir=tools .`
   must print nothing (the sync tool itself names the old path).
8. Verify: `go vet ./...` and `go test ./...` in `db/` (this includes the sync tool's own
   tests), `go vet ./...` in `db/examples`, then regenerate the test models and run the
   PostgreSQL, CockroachDB, MySQL, MariaDB and SQLite suites as `db/tests/Readme.md`
   describes. A known failure that now passes fails the run: remove its entry and row.
9. Open one PR, `chore(db): merge go-jet vX.Y.Z`, with the `-stat` output of step 2 and the
   resolved conflicts in the description. Send generic fixes from the table upstream
   (rule 4) if they are not there yet.

## Release order

`db` depends on `pkg/functional`, which is its own module. Tag `pkg/functional/vX.Y.Z` first,
then require it in `db/go.mod` in a release commit and tag `db/vX.Y.Z`. The root module requires both, and is tagged
last. [RELEASING.md](../RELEASING.md) has the exact steps. `go.work` at the repository root is
for development only.
